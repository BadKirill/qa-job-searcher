# План разработки многопользовательской платформы

Дата плана: 11 ноября 2026 года. Этапы 0–9 завершены;
этап 10 частично выполнен на рабочем Mac 15 ноября. Проверки и ограничения —
в `verification.md`.

Цель — дать 10–20 пользователям возможность одновременно пользоваться одним сайтом.
У каждого свой вход, набор источников, критерии поиска, эталон CV, подтверждённые
факты, диалоги, выдача, Applied, архив и документы. Разные профессии поддерживаются
с первого запуска. Доступ выдаётся по приглашениям. OpenAI API-проект и серверный
API-ключ остаются общими; контекст, сессии, задания и учёт использования разделены.

Это основной план следующей разработки. Он заменяет положения о единственном
владельце, общей конфигурации поиска и SQLite как целевом хранилище в
[предыдущем плане](web-app-plan.md). Требования к фактам, проверке документов,
минималистичному оформлению, языкам документов и качеству сохраняются, если ниже
нет явного изменения. Правила репозитория находятся в [AGENTS.md](../AGENTS.md).

## 1. Зафиксированный объём первой версии

- Один аккаунт соответствует одному личному пространству. Командные пространства
  и совместное редактирование чужого профиля в этот этап не входят.
- Регистрация только по приглашению администратора. Логин и пароль, смена пароля,
  завершение сессий, отключение аккаунта и одноразовое восстановление доступа.
- Один действующий профиль поиска на человека, содержащий несколько названий ролей,
  синонимы, предпочтения и ограничения. История его версий сохраняется.
- Один активный эталон CV на человека, черновики и предыдущие версии.
- Управление своими источниками через сайт: включение агрегаторов, добавление
  поддерживаемых карьерных досок и публичных Telegram-каналов.
- Профессии задаются пользователем; алгоритм не требует принадлежности к QA.
- Независимые статусы вакансий, история, поиск по расписанию и по кнопке.
- Генерация CV и cover letter, диалоги, проверка, просмотр и скачивание в своём кабинете.
- Один общий OpenAI API-ключ на сервере, персональные квоты и общий предел нагрузки.
- Полный перенос имеющихся данных в аккаунт текущего владельца.

Платёжная система, подписки, автоматические отклики, произвольный скрейпинг сайтов,
приватные Telegram-каналы и пользовательские ключи OpenAI не входят в эту версию.
Источники без поддерживаемого API/фида остаются ручными ссылками с явной отметкой.

## 3. Целевая архитектура

Сохраняем React/TypeScript, FastAPI, существующий рендер документов и ограниченный
MCP по stdio. Целевая база — PostgreSQL. Для доступа к данным планируются
SQLAlchemy 2, psycopg 3 и Alembic с закреплёнными версиями зависимостей.
SQLite остаётся форматом чтения старых данных при переносе; одновременно
поддерживать два основных backend хранилища после перехода не требуется.

PostgreSQL выбирается для транзакций, ограничений целостности и нескольких
исполнителей очереди. Небольшой многопользовательский запуск технически возможен
и на SQLite; переход не является условием самой изоляции пользователей.

Путь запроса: браузер → FastAPI → текущий пользователь → персональный сервис
и репозиторий → PostgreSQL. Долгая работа: API → сохранённое задание → исполнитель
→ источники или OpenAI/MCP → проверенный результат → событие владельцу.

В первой версии очередь находится в PostgreSQL. Redis, Celery и отдельный брокер
для этого масштаба не добавляются. API, планировщик и исполнители запускаются
отдельными процессами; их можно перезапускать независимо.

Приватные файлы сохраняются в существующем файловом хранилище с пространством
имён пользователя и задачи. Физическое разделение каталогов дополняет проверку
доступа в базе; само по себе оно не является авторизацией.

### 3.1. Модель данных

Имена ниже — целевая логическая схема. Окончательные имена и DDL фиксируются
в миграциях этапа 1 до переноса рабочих данных.

| Сущность | Содержание и ограничения |
| --- | --- |
| `users` | ID, нормализованный уникальный логин, отображаемое имя, хеш пароля, роль, состояние аккаунта, даты |
| `sessions` | Хеш токена, `user_id`, CSRF, срок действия, отзыв; секретный токен не хранится открыто |
| `invitations` / `password_reset_tokens` | Хеш одноразового токена, назначение, создатель, срок, использование и отзыв |
| `source_definitions` | Технические типы поддерживаемых публичных источников и допустимые параметры |
| `user_sources` | `user_id`, тип, нормализованные параметры подключения, включение и версия |
| `search_profiles` | `user_id`, версия, роли/синонимы, ограничения, предпочтения и правила неизвестных значений |
| `jobs` / `job_identities` | Содержание объявления, внешние идентификаторы, происхождение, исходная география, хеш содержания; без персонального score |
| `source_fetches` / `source_fetch_jobs` | Какие объявления вернул конкретный публичный источник/запрос, время, состояние, полнота и ошибки |
| `search_runs` / `search_run_jobs` | Владелец, версии настроек, использованные получения источников, персональный score/причины, зафиксированный порядок |
| `user_jobs` | Пара `(user_id, job_id)`, Applied и архив; независима от свежего score и наличия в новом поиске |
| `candidate_templates` | Владелец, версия, draft/active/retired, подтверждённые факты, инструкции, исходный файл и reference |
| `conversations` / `messages` | Владелец, контекст, сообщения и порядок; scope уникален внутри аккаунта |
| `tasks` / `task_requests` | Владелец, kind, scope, request ID, неизменяемые входы, статус, lease, попытки, отмена и результат |
| `artifacts` | Владелец, задача, приватный путь, формат, хеши и действующая проверка |
| `user_revisions` | Персональный номер изменения для SSE и восстановления после переподключения |
| `usage_events` / `usage_reservations` | Пользователь, задача, роль API-вызова, внешний ID, usage/неизвестный исход и резерв квоты |
| `telegram_bindings` | Явное соответствие Telegram-аккаунта пользователю сайта |
| `schema_migrations` / `import_runs` | Версии схемы и идентификаторы проверенных запусков импорта |

Ограничения целостности:

- У персональных сущностей `user_id` обязателен. Связи задача–эталон,
  диалог–сообщение и задача–артефакт не допускают разных владельцев; это обеспечивают
  составные внешние ключи/уникальные ключи и серверные проверки.
- Активный эталон и действующий профиль поиска уникальны внутри пользователя.
- Идемпотентность уникальна по пользователю и request ID; один и тот же ключ
  с другим содержимым даёт конфликт. Scope активного задания также включает владельца.
- ID вакансий, исторические fingerprints и внешние ID не пересоздаются произвольно.
- Публичная запись вакансии не содержит резюме, диалоги, личные оценки или статусы.
- Удаление подключения источника не удаляет Applied, архив, диалоги и документы.
- Межпользовательский доступ к персональным данным закрыт и по прямому ID.

### 3.2. Изоляция доступа

Ввести обязательный `CurrentUser` из серверной сессии. Обычный API не принимает
`user_id` как способ выбора владельца. Персональный репозиторий создаётся с
обязательным владельцем и не имеет режима «вернуть все данные» по умолчанию.

Административные операции вынести отдельно. Роль администратора позволяет управлять
приглашениями, состоянием аккаунтов и квотами; просмотр чужого CV через обычный
пользовательский API она автоматически не разрешает. Доступ оператора к самой базе
и диску остаётся отдельной эксплуатационной границей.

Чужие персональные ID возвращают 404 без раскрытия содержания. Отсутствующая
сессия даёт 401; запрещённая административная операция — 403. Сохраняются проверки
CSRF, Origin, Host, размера запросов, безопасных путей и содержимого файлов.
Нельзя объединять кэши документов, сообщений и профилей разных людей.

### 3.3. Поиск и общие публичные данные

Сначала получить объявления по подключённым пользователем источникам, затем
применить его фильтры и вычислить его score. Не сохранять в общем каталоге только
результат фильтра первого пользователя. При обработке не изменять общий объект Job
персональными полями; matching возвращает самостоятельный результат.

Ключ кэша публичного запроса включает адаптер, версию, доску/канал, регион API,
поисковый запрос, параметры, страницу и окно свежести. Объединяются только одинаковые
публичные запросы. У каждого пользователя сохраняется собственный search run.
Подключения, список интересов и статистика одного человека другим не раскрываются.

Для каждого источника нужна таблица возможностей: профессии/категории, параметры
поиска, география, форматы работы, пагинация, ограничения окна и полнота описания.
Неподдерживаемый параметр не изображается работающим фильтром источника. Где возможно,
он применяется локально по полному объявлению. Ограниченная полнота показывается в UI.

Персональный профиль задаёт должности и синонимы, разрешённые/исключённые уровни,
географию кандидата и допустимой работы, remote/hybrid/onsite, обязательные условия,
предпочтительные навыки и домены, порог релевантности. Для неизвестных значений
задаётся явное поведение. Зарплата сравнивается только при сопоставимых валюте,
периоде и данных; отсутствующие сведения не превращаются в подтверждённое совпадение.
Язык объявления не равен требуемому языку работы.

Сохранение фильтра создаёт версию. Задание использует версии настроек на момент
создания; устаревший параллельный результат не заменяет выдачу для более новой версии.
Новая выдача не меняет порядок уже открытого снимка. Старые документы и пользовательские
статусы доступны владельцу и после изменения поиска или удаления источника.

### 3.4. Один OpenAI API на всех

Использовать существующий проект, API-ключ и конфигурацию модели на сервере.
Пользователь не получает ключ и не вводит свой. Общий сохранённый агент допустим,
но каждая генерация, factual review, visual review и чат получают отдельную сессию
с контекстом своей задачи. Общей истории общения между аккаунтами нет.

Владелец передаётся из задания в gateway и MCP TaskScope без значения по умолчанию.
Проверяются владелец, задача, версия эталона, роль и срок разрешения. Сохраняются
`environment: none`, пустые инструменты и vault IDs, запрет делегирования и
проверка эффективной конфигурации. Модель не устанавливает статус ready.

Каждый вызов возвращает свой ответ и метаданные. Убрать зависимость от общего
изменяемого `last_run_metadata`, который может смешать параллельные выполнения.
Usage записывается для всех этапов, включая исправления, чаты и отрицательные проверки,
если провайдер предоставил сведения. Неизвестный usage не записывается как нулевой.

Квоты применяются по пользователю и глобально, с атомарным резервированием до запуска.
Повтор того же запроса не списывает квоту второй раз; неопределённый исход сетевого
запроса не вызывает слепую повторную платную генерацию. Полученные внешние ID
сохраняются для сверки. Лимиты числа заданий/токенов отличаются от оценки денег:
стоимость помечается оценкой с версией тарифа; точный счёт остаётся у провайдера.
При неизвестном исходе резерв не освобождается как заведомо неиспользованный.

Численные квоты и денежный бюджет настраиваются администратором; в плане не
утверждается конкретная сумма расходов. Фактические лимиты провайдера проверяются
до пилота. Общий rate limit обрабатывается всеми исполнителями согласованно.

### 3.5. Параллельность и очередь

Стартовые технические настройки для проверки: до двух документных заданий
одновременно на платформу, до одного документного задания на пользователя,
отдельные исполнители поиска и чата. Число одновременно активных OpenAI-вызовов
ограничено общим конфигурируемым пределом, первоначально два. Эти значения
проверяются нагрузкой и доступными лимитами API, а не означают обещанную пропускную способность.

Выбор задания — короткая транзакция с блокировкой строк и `SKIP LOCKED`, проверкой
глобальных/персональных слотов и атомарной выдачей lease. Долгие сетевые операции,
рендер и ожидание модели выполняются вне транзакции. Персональные слоты также
захватываются атомарно, чтобы два исполнителя не обошли лимит одновременно.

Исполнитель обновляет lease. Завершение принимается только от действующего
исполнителя с актуальной версией захвата. Поздний результат отменённого или
перехваченного задания не публикуется. Артефакты регистрируются только после
повторной проверки права завершить задачу и целостности файлов.

Очередь обслуживает пользователей по очереди с ограничением активных заданий;
поток поисков не вытесняет документы, длинная генерация не блокирует просмотр сайта.
Планировщик создаёт задания отдельно по аккаунтам, исключает дубли при нескольких
процессах и распределяет запуски во времени. Неактивные аккаунты не запускают новые
платные задачи. При отключении аккаунта отзываются сессии и новые захваты; активные
вычисления отменяются по возможности, их поздние результаты не выдаются.

## 4. Порядок реализации

Каждый этап включает код, применимые тесты, документацию и фактическую запись
проверок. Следующий этап использует проверенные контракты предыдущего. Промежуточную
версию без полной изоляции не открывать приглашённым пользователям.

Уточнение пользователя от 11 ноября 2026: на каждом этапе выполнять frontend/backend
unit, API, integration и browser E2E. После завершения этапа дополнять
[вики проекта в Notion](https://app.notion.com/p/4157e1830c3280999805ccb6f1d6ea95)
выполненными изменениями, проверками и ограничениями. Первая запись также фиксирует
исходное состояние. Аудит и матрица источников этапа 0 находятся в
[исходном состоянии](multi-user-baseline.md).

| --- | --- |
| Аккаунт | `GET /api/me`, login с логином/паролем, session/logout, смена пароля, отзыв сессий |
| Приглашения | `POST /api/invitations/accept`: атомарная проверка токена и активация пустого аккаунта, зарезервированного администратором |
| Восстановление | `POST /api/password-resets/accept`; выдача/отзыв одноразовой ссылки администратором |
| Источники | `GET/POST /api/sources`, `PATCH/DELETE /api/sources/{id}`, проверка подключения |
| Поиск | `GET/PUT /api/search-profile` с ожидаемой версией, персональные search-runs и история |
| Использование | `GET /api/usage` со своими квотами, usage и отмеченными неизвестными значениями |
| Администрирование | Отдельные `/api/admin/*` для приглашений, аккаунтов, квот и агрегированной диагностики |

Имена дополнительных маршрутов закрепляются в API-тестах при реализации этапов.
Изменяющие операции требуют CSRF, валидации и контроля версии там, где возможна
потеря параллельных изменений. Долгая работа возвращает 202 и task ID.
Конфликт версии/идемпотентности даёт 409, ошибка параметров — 422,
превышение квоты/частоты — 429 с понятной причиной.

Новая установка использует защищённый bootstrap администратора. После миграции
глобальная `/api/setup` не позволяет заново назначить владельца существующим данным.
Отправка приглашений по email не требуется: администратор получает ссылку в UI.

## 6. Проверки и критерии приёмки

Действуют [политика тестирования](testing-policy.md) и
[модель безопасности](agent-safety.md). Для каждой функции нужны позитивные,
негативные и краевые сценарии на соответствующих уровнях. Процент покрытия
не заменяет интеграционные и браузерные проверки.

| Проверка | Обязательный исход | Уровни |
| --- | --- | --- |
| Приглашение | Одноразовое использование; истёкший/отозванный токен не создаёт аккаунт; два конкурентных принятия дают один успех | Unit, API, integration, E2E |
| Сессии | Вход А/Б независим; logout, смена пароля и отключение отзывают доступ и SSE | API, UI, E2E |
| Чужие ID | Для job history, snapshot, source, template, conversation, task, artifact, страниц PDF и удаления нет чтения/изменения чужих данных | API, integration, критические E2E |
| Целостность | Нельзя связать задачу А с шаблоном/артефактом Б даже внутренним ошибочным вызовом | Integration на PostgreSQL |
| Разные профессии | QA, разработчик и дизайнер получают собственные результаты; Junior и hybrid вне Сербии доступны при соответствующем профиле | Unit, adapters, integration, E2E |
| География | Сохранены полные исходные ограничения; узкое ограничение не теряется при нормализации | Unit, adapter/API contracts |
| Личные источники | Отключённый/чужой источник не попадает в выдачу; удаление не стирает историю и документы | API, UI, E2E |
| Одна вакансия | Разные score/причины; Applied/архив А не меняют Б; совместное обновление не перезаписывает оценки | Integration, API, E2E |
| Версии | Смена фильтра/эталона во время выполнения не меняет закреплённые входы; старый поиск не заменяет новый | Integration, UI, E2E |
| Снимки | Пагинация и собственный снимок устойчивы; чужой snapshot закрыт; 10 карточек на полной странице | API, UI, E2E |
| Два документа | Контексты, API-сессии, facts, метаданные и файлы А/Б не смешиваются; общий ключ остаётся серверным | Integration, E2E, реальный API/MCP smoke |
| Проверка документа | Отрицательный/невалидный/недоступный reviewer, подмена хеша и чужой scope блокируют preview/скачивание | Unit, API, integration, E2E |
| Идемпотентность | Повтор внутри аккаунта не дублирует работу; одинаковый request ID у А/Б не объединяет задания | API, integration, E2E |
| Несколько workers | Один захват; атомарные лимиты; heartbeat; рестарт, истёкший lease, отмена и поздний ответ не публикуют дубль | Integration с несколькими процессами |
| Квоты/API | Общие и персональные пределы не обходятся гонкой; 429/timeout/unknown usage не дают нулевой расход или слепой повтор | Unit, API, integration |
| Смена аккаунта | Старые запросы, события, preview и React state не показывают данные А после входа Б | UI, E2E |
| Telegram | Явная привязка, персональная выдача, сохранённые доставки, отсутствие второго polling-процесса | Integration, API/команды |
| Миграция | Счётчики/ID/связи/хеши совпадают; повтор без дублей; повреждение и неполный импорт не публикуются | Integration, репетиция восстановления |

Весь собственный backend и frontend должны отдельно проходить минимум 90% строк
и 90% ветвлений. Измерение включает новые миграции, команды импорта, scheduler,
административные операции и не импортированные тестами исходные файлы.
SQLite не подменяет PostgreSQL в проверках транзакций, блокировок и ограничений.

Реальная проверка OpenAI/MCP использует синтетические профили и шаблоны.
Контрактные mocks и E2E fixture gateway не доказывают работу живого API.
Недоступный ключ/баланс фиксируется как незавершённая проверка, а не как успех.
Персональные резюме и секреты не публикуются в CI, логах и тестовых трассах.

### Нагрузочная приёмка

Зафиксировать CPU, RAM, версии, число процессов, объём тестовой базы и параметры
запуска. Использовать не менее 10 000 синтетических объявлений и 20 аккаунтов.
Сценарий: 20 авторизованных браузерных/HTTP-сессий читают выдачу и события, меняют
свои статусы и создают задания в течение 10 минут; исполнители обрабатывают
контролируемые задержки и ошибки источников/API.

Начальные цели для тестового окружения: p95 обычного чтения API до 500 мс,
постановки задания до 1 секунды, без неожиданных 5xx, потери данных, двойного
исполнения или нарушения принадлежности. Ожидаемые 401/404/409/429 проверяются
отдельно. Эти цифры — критерии проверки, не измеренные результаты и не гарантия
времени ответа внешних источников или генерации OpenAI.

Длительность генерации и ожидание очереди измеряются отдельно. Проверить,
что перегрузка одного пользователя не останавливает прогресс других и что
после рестарта восстанавливаются персональные состояния без повторной оплаты
неопределённых внешних вызовов. Реальный API-smoke выполняется отдельно от
нагрузочного теста, чтобы тест нагрузки не порождал неконтролируемые расходы.

## 7. Условия завершения разработки

- [ ] Все этапы имеют выполненные задачи и фактические результаты проверок.
- [ ] Два синтетических пользователя разных профессий проходят весь браузерный
  путь от приглашения до поиска, настройки CV и скачивания проверенных документов.
- [ ] Проверки чужих ID, разных сессий и смены аккаунта проходят полностью.
- [ ] История владельца, архив, Applied, Telegram deliveries и файлы сохранены;
  проблемные старые документы явно отражены, а не потеряны или молча одобрены.
- [ ] Параллельная очередь, квоты общего API и отказные сценарии проверены.
- [ ] Есть отдельные отчёты покрытия backend/frontend и проходящий полный gate.
- [ ] Есть реальный OpenAI/MCP smoke и фактический отчёт нагрузочной проверки.
- [ ] Проверены резервная копия, восстановление, переключение и границы отката.
- [ ] Документация запуска, угроз, тестов и фактических ограничений соответствует коду.

На этапе планирования не создавать репозиторий, не пушить, не создавать PR
и не переключать рабочий сервис. Во время разработки отмечать выполненные пункты
только после проверки; дату, команды, результаты и ограничения вести в
`verification.md`. Существенное изменение архитектуры сначала отражать здесь
и в соответствующих контрактах, чтобы дальнейшая работа шла по одному плану.

## Доработки поиска по обратной связи

Требования, порядок работ и ссылки на первичные источники собраны в
[плане доработки поиска](../../docs/search-feedback-development-plan.md).

Профиль поиска использует прежние неизменяемые строки `search_profiles` и
метаданные именованных вариантов в пространстве владельца. Старые строки доступны
по исходным номерам. Удаление варианта скрывает его в интерфейсе, а поиски сохраняют
ссылки на зафиксированные критерии. При обновлении критерия текущего варианта
создаётся ревизия. Отдельное переключение варианта меняет активную ревизию и
счётчик активации. Фоновый поиск сравнивает этот счётчик перед публикацией.

Миграция `0008_posting_tasks` добавляет вид задания `posting_check` в существующую
очередь. Downgrade возвращает ограничение предыдущей схемы и завершится ошибкой,
если в базе уже есть задания этого вида. Сохранённые строки не удаляются.

Вкладка «Добавленные вручную» показывает локальные вакансии пользователя. Для
совместимости с внешними ключами создаётся нейтральная строка `jobs`. Описание,
ссылка и пользовательские поля сохраняются в `job_matches` владельца. Архив,
отклики и документы используют прежние отношения с подтверждённой личной вакансией.

Проверка оригинала выполняется в очереди поиска в рамках ограничения её
параллельности. ATS-ответ устанавливает статус объявления. Web Search предлагает
ссылки для проверяемой публичной вакансии и использует общие и личные квоты OpenAI.
Быстрый просмотр показывает подтверждённые поля и их источники. Отдельно видны
язык команды, требования к языкам и признаки, на которых основаны предположения.
