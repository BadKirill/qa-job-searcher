# Личные источники и профиль поиска

PostgreSQL-веб-приложение предоставляет раздел «Поиск и источники» для каждого
аккаунта. Новый пользователь начинает без профиля и подключений. Личные доски,
каналы и критерии владельца ему не копируются. Рабочее переключение и общие
исполнители всех пользователей остаются следующими этапами плана.

## Настройка через сайт

1. Открыть «Поиск и источники». Ввести названия ролей и синонимы через запятую.
   При необходимости задать до восьми запросов агрегаторам; иначе используются
   первые восемь названий ролей. Навыки, отрасли, направления и предпочтительные
   уровни повышают оценку, исключения названий отбрасывают вакансии.
2. Выбрать remote, hybrid и/или on-site, минимальную оценку, географию и допустимость
   Junior. У нового профиля нет скрытых QA/Junior/Serbia-правил. Дополнительные
   QA-названия включаются отдельным флагом. Пустой список стран не ограничивает
   географию; список мест кандидата позволяет проверять явные исключения работодателя.
3. Сохранить профиль. Примеры QA, разработки и дизайна применяются отдельной кнопкой:
   заменяют профиль и добавляют отсутствующие пять агрегаторов. Имеющиеся подключения
   сохраняются, выключенные источники не включаются повторно. QA-пример явно содержит
   прежние ограничения владельца, включая Junior и Serbia hybrid.
4. Добавить нужные агрегаторы, Greenhouse/Lever/Ashby-доски или публичные Telegram-каналы.
   Для доски нужен идентификатор, для канала — handle, а не произвольный URL.
   Lever поддерживает Global/EU. Можно изменить параметры, выключить и удалить источник.
5. «Проверить» запрашивает один ответ источника и проверяет его формат. Результаты:
   доступен с количеством объявлений, доступен и пуст, недоступен с объяснением.
   Это не полная проверка пагинации, не результат matching и не гарантия подлинности
   объявления. За минуту разрешены пять проверок на пользователя.
6. После настройки запустить поиск. Без сохранённого профиля или включённых корректных
   источников API вернёт 409 с предложением закончить настройку.

Несохранённый профиль не сбрасывается при редактировании источников. Если другая
вкладка уже сохранила новую версию профиля/подключения, сервер отклоняет устаревшую
запись с 409. Черновик остаётся видимым; «Загрузить актуальные настройки» явно
заменяет его сохранённой версией. Повторное применение примера тоже проверяет версии.

## Контракт API

Все маршруты требуют сессии; изменения дополнительно Origin/CSRF. Владелец берётся
из сессии. Администратор не получает доступ к чужим настройкам по ID.

| Маршрут | Результат или тело |
| --- | --- |
| GET `/api/search-settings` | Профиль и коллекция источников с версиями |
| GET/PUT `/api/search-profile` | Чтение; запись `{expected_version, profile}` |
| GET `/api/search-profile/history` | Все личные версии профиля |
| GET `/api/source-types` | Девять типов и ограничения каждого |
| GET `/api/search-presets` | Явные примеры профиля |
| POST `/api/search-presets/{name}/apply` | `{expected_version, expected_sources_version}` |
| GET/POST `/api/sources` | Коллекция; создание `{kind, enabled?, config?}` |
| PATCH `/api/sources/{id}` | `{expected_version, enabled?, config?}` |
| DELETE `/api/sources/{id}` | `{expected_version}`; удаление с сохранением истории |
| GET `/api/sources/{id}/history` | История подключения, включая запись удаления |
| POST `/api/sources/{id}/check` | `{expected_version}`; status/items/reason/stale и проверенные версии |

Профиль хранится в `search_profiles`; одновременно активна одна версия. Ревизия
`0004_search_settings` добавляет `source_versions`, переносит туда текущие подключения
и сохраняет старые SQL-ревизии. История переживает удаление текущей строки. Импорт,
выполненный уже после четвёртой ревизии, также остаётся редактируемым: исходная версия
добавляется в историю перед первым изменением. Изменения сериализуются блокировкой
аккаунта и сравнивают ожидаемую версию в той же транзакции. Дубли подключений
определяются внутри одного пользователя, между пользователями допустимы.

Проверка подключения не держит транзакцию во время сети. После ответа версии
сравниваются повторно: изменение/удаление источника или профиля даёт `stale=true`.
Проверка никогда не публикует вакансии и не меняет личную выдачу.

## Адаптеры и сеть

Himalayas и Remote.com получают личные запросы; Hirify больше не ограничивает сбор
QA/remote. Greenhouse получает детали вакансий разных ролей, Telegram не фильтрует
посты по принадлежности к QA. Фильтрация и оценка происходят после сбора. Сохраняются
все страны Himalayas/Hirify, исключения Remote.com и полный географический контекст
Telegram. Упоминание QA в обязанностях не превращает Backend-заголовок в QA-вакансию.
Существующее разрешение внешних идентичностей сохраняет ID при изменении location.

В новом pipeline используется `SourceClient`: только GET/HTTPS к десяти фиксированным
хостам провайдеров, порт 443, без URL credentials, env proxy и автоматических redirects.
Параметры досок/каналов валидируются отдельно, внешние URL из вакансий не fetch-ятся.
DNS ограничен тремя секундами; проверяются все ответы, приватные, loopback, link-local,
reserved и multicast адреса запрещены. Публичный IP закрепляется на срок клиента;
Host и TLS SNI сохраняют исходное имя, TLS-проверка включена. Разные hostname
используют разные соединения даже при совпадении IP.

Таймаут HTTP по умолчанию 15 секунд, в поиске берётся серверный HTTP_TIMEOUT_SECONDS.
Это таймаут сетевых операций, а не общий дедлайн всего поиска. На запуск ограничены
2048 запросами и 64 MiB суммарно на запуск. У каждого подключения свой клиент:
до 16 запросов, у Remote.com до 1024 запросов для максимум восьми выдач по 100
объявлений и их деталей. До четырёх подключений загружаются одновременно,
у клиента до четырёх запросов одновременно. Ответ ограничен 8 MiB, для полной
доски Greenhouse — 32 MiB; меньший явно заданный предел сохраняется. Общий предел
64 MiB действует и для крупных досок. Не более 128 включённых источников на поиск;
превышение отклоняется до постановки задания. Поток закрывается при превышении;
сжатие ответов запрещено, запрашивается identity. Ошибки выводятся как безопасные
коды/классы без тел провайдеров и внутренних адресов. Проверка подключения имеет
бюджет один запрос. Общие rate limits провайдеров между пользователями пока не добавлены.

| Источник | Доступное окно |
| --- | --- |
| Remotive | Публичная текущая выгрузка |
| Himalayas | Первая страница для первых восьми запросов |
| We Work Remotely | Текущая RSS-лента |
| Remote.com | До 100 результатов на каждый из восьми запросов, затем детали в отдельном бюджете подключения |
| Hirify | Первые три страницы |
| Greenhouse | Одна доска с полными описаниями одним запросом `content=true` |
| Lever | Одна доска, выбранный Global/EU API |
| Ashby | Опубликованные вакансии одной доски |
| Telegram | Две страницы публичного канала |

География определяется текстовыми правилами и явными полями источника. Полная
международная нормализация стран, налоговых правил и разрешений на работу не заявляется.
Вакансии с неясной географией требуют соответствующего флага; они остаются в review
отчёта. Закреплённые входы, история и атомарная публикация описаны в
[personal-search-runs.md](personal-search-runs.md).

## Границы запуска и проверок

Веб-поиск закрепляет персональные настройки при постановке задания в очередь.
CLI Worker пока обслуживает существующего владельца `WEB_OWNER_ID`; ненастроенный
поиск пропускается, после настройки доступен ручной запуск.
Общий scheduler, параллельные исполнители и квоты появятся на следующих этапах.
SQLite/TOML-путь временно сохраняет прежний режим для регрессий и старой установки.

Unit-проверки покрывают профиль, matching и сетевые границы, API/integration используют
настоящую PostgreSQL и конкурентные записи. Browser E2E проходит двух приглашённых
пользователей через формы, источники, профиль, настоящий Worker/адаптеры/matching,
сохранение/reload и конфликт вкладок. Ответы провайдеров и DNS в тестах управляемые;
живые источники и OpenAI этим прогоном не проверяются. Числа полного gate находятся
в [verification.md](verification.md).
