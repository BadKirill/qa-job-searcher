# Личные эталоны, диалоги и документы

Этап 6 [плана личных кабинетов](multi-user-development-plan.md).
Один серверный OpenAI API-проект обслуживает разные личные пространства. Общий ключ
не объединяет факты, исходные файлы, историю обсуждения или агентские сессии.

## Как пользоваться

1. В своём кабинете открыть «Профиль и шаблон», загрузить PDF/DOCX, проверить
   извлечённые факты и подтвердить сохранение эталона. Черновик не заменяет активную версию.
2. Открыть текущую выдачу либо выбрать запуск в «Истории поиска».
3. Нажать «Сделать CV» или создание письма в карточке. Задание закрепляет
   выбранную версию вакансии и действующий подтверждённый эталон.
4. В блоке документа видны имя исходного эталона, время его подтверждения и название
   вакансии. Смена профиля после постановки в очередь не меняет это задание.
5. Для правок открыть диалог документа и нажать «Сгенерировать заново».
   Используются выбранная версия вакансии, сообщения её диалога и активный на момент
   нового запроса эталон. Новые сведения подтверждаются в форме профиля.
6. Готовые файлы доступны после factual и visual проверок. Удаление документа
   требует подтверждения и удаляет собственные файлы выбранного задания.

CV остаётся английским; язык письма определяется по описанию вакансии. Профессия
берётся из вакансии и подтверждённых фактов. QA-пресет поиска сохраняет своё прежнее
поведение, но генерация не требует QA-специализации. Поля QA-деталей отображаются
только при наличии соответствующих сведений в объявлении.

## Закрепление контекста

`pg_document_context.py` выполняет выбор входов и постановку задания в одной
PostgreSQL-транзакции под блокировкой аккаунта. Контекст содержит:

- владельца из авторизованной сессии;
- личную копию содержания вакансии, её ID и `job_version` с run/snapshot/content hash;
- полную активную версию эталона, подтверждённые факты, стиль и PDF reference;
- последние 16 сообщений своего диалога и последние восемь реплик пользователя.

Request ID привязан к намерению запроса. Повтор возвращает исходное задание даже
после изменения эталона. Переиспользование ключа с другими параметрами даёт 409.
Одинаковый активный контекст объединяется в одно задание внутри владельца.
Чужие job, snapshot, run, template и conversation недоступны, включая администратора.

Диалог вакансии адресуется хешем её содержания внутри владельца. Изменившееся
содержание получает отдельную переписку; одинаковый текст в нескольких запусках
может использовать прежнее обсуждение. При явном выборе snapshot/run задание
всё равно закрепляет именно этот источник версии. Повтор из одного `conversation_id`
без выбора snapshot/run использует сохранённую в диалоге вакансию.

Старый диалог `job:<id>` без закреплённого содержания присоединяется к версии,
совпадающей с доступной текущей личной карточкой. Его ID и сообщения сохраняются.
Миграция не восстанавливает содержание, утраченное до его закрепления.

Задание чата также атомарно сохраняет свою реплику и неизменяемые входы. Для
настройки эталона используется выбранный собственный черновик; для диалога вакансии
— свой активный эталон. Нельзя отправить второе сообщение до ответа на первое.
Отсутствие активного эталона при генерации откатывает создание диалога и задания.

## API

| Маршрут | Дополнение |
| --- | --- |
| `POST /api/conversations` | Для `job_id` поддерживает `snapshot_id` и `run_id`; проверяет членство вакансии и владельца |
| `POST /api/jobs/{id}/documents` | `kind`, `language`, `request_id`; необязательные `snapshot_id`, `run_id`, `conversation_id` |
| `POST /api/conversations/{id}/messages` | `text`, `request_id`; собственный диалог и атомарная постановка чата |
| `GET /api/tasks/{id}` | `input_summary` с именем/версией эталона, подтверждением, вакансией и манифестом её версии |
| `GET /api/templates/{id}/source` | Собственный исходник, проверка пути и контрольной суммы |
| `GET /api/artifacts/{id}/preview` и `/download` | Собственный ready artifact, проверка пути, хешей и результата проверок |
| `DELETE /api/tasks/{id}` | Только собственное законченное задание, безопасное удаление его каталога |

Выбор несовместимых run/snapshot или диалога другой версии даёт 409; чужой объект
и отсутствие вакансии в выбранном результате — 404. Историческая карточка без
доступного описания требует обновления до генерации. Невалидный Unicode/NUL
пользовательского JSON отклоняется с 422 до PostgreSQL.

Frontend передаёт snapshot из показанной карточки в генерацию и чат, а для повторной
генерации — ещё conversation ID. При смене снимка карточки пересоздаются; при смене
контекста чата сбрасываются история, черновик ввода и состояние повторного запуска.
Запоздавшие ответы размонтированного контекста не подменяют новый.

## Gateway и MCP

Gateway не хранит общего результата последнего запроса. Каждый вызов создаёт
собственный transport/session и возвращает `AgentResponse` либо `AgentText` с
копируемыми метаданными. Worker передаёт независимые копии контекста, черновика,
визуального reference и сообщений; изменение объекта внутри gateway не меняет
закреплённые подтверждённые факты.

`scope_context` требует явные непустые owner/task/template ID. В MCP scope закреплены
владелец, задача, ID и версия эталона, роль, срок и хеш передаваемого содержания.
Проверка выполняется при перечислении и каждом вызове инструмента. Передавать
чужой ID или путь через аргументы инструмента нельзя. Изменение фактов после
создания scope приводит к отказу. Файл контекста читается через единственный
дескриптор с `O_NOFOLLOW`: проверяются обычный файл, владелец, приватный режим,
размер и фактически прочитанный объём. Внешние страницы и сообщения остаются данными.

Генератор, factual reviewer и visual reviewer вызываются независимо. Сохранены
схемы фактов, assessment адаптации, хеши, визуальные ограничения и максимум две
коррекции после первой попытки. Отрицательная, отсутствующая или невалидная проверка
не даёт ready/download. Worker сверяет owner/task/role/template metadata ответа.
Тестовые внедрённые gateway могут возвращать обычные dict/str без transport metadata;
реальный gateway возвращает привязанные метаданные для каждого вызова.

## Файлы и атомарное завершение

Новые файлы PostgreSQL-пользователя находятся в
`data/users/<sha256(user_id)>/templates/` и
`data/users/<sha256(user_id)>/artifacts/<task_id>/attempt-<uuid>/`.
Каталоги создаются с 0700, исходные загрузки — 0600 с эксклюзивным созданием.
Идентификатор пользователя не становится именем файла и не передаётся в пути браузеру.
Запрещены выход из корня, `..`, симлинки и чужой namespace. Создание каталога
документов начинается после положительной проверки фактов.

Для уже импортированных файлов сохраняется чтение прежних `data/templates` и
`data/artifacts/<task_id>` после проверки владельца строки БД, пути и хеша.
Новые файлы туда не записываются. Явно внедрённый SQLite-путь оставлен для регрессий
и импорта; он задаёт совместимый owner на границе worker, но gateway/MCP его не выводят
по умолчанию. Новые пользовательские HTTP-запросы используют PostgreSQL-владельца.

Рендер PDF/DOCX и их проверка выполняются до записи готовности. `finish_document`
под блокировкой проверяет live lease, worker, статус rendering, хеш исходных входов,
версию эталона и job version. Регистрация всех артефактов и ready — одна транзакция;
отмена или потеря lease не оставляет частично зарегистрированных ready-файлов.
Файлы незавершённой/потерявшей lease попытки могут остаться на диске, но не выдаются
API. Автоматическая уборка таких каталогов пока не реализована.

Нативный PDFium не является потокобезопасным: построение изображений reference
сериализовано процессным RLock. Сетевые агентские сессии и остальное исполнение
разных задач этим lock не объединяются. Безопасность путей предполагает доверенный
локальный runtime; защиты от оператора с правами замены каталогов во время чтения нет.

## Проверки и границы

`tests/test_personal_documents.py` проверяет PostgreSQL-транзакции, неизменяемые
исторические входы, независимую активацию, сообщения, идемпотентность, неверные
версии/владельцев, private paths, миграцию и отказ позднего завершения. Два worker
с одним внедрённым gateway запускаются через `asyncio.gather`; реальные PDF/DOCX
содержат только факты своего синтетического кандидата.

Отдельная интеграция использует настоящий MCP stdio и настоящий OpenAITransport с
контролируемым HTTP-контрактом. Параллельные генератор/проверяющий для двух людей
получают четыре разные сессии и факты своих владельцев. Это не вызов живого OpenAI API.

Frontend component/API-adapter тесты проверяют передачу snapshot/conversation,
сводку закреплённых входов и очистку старого чата при задержанном ответе. Browser E2E
проходит двух приглашённых людей разных профессий: свои DOCX, активация, поиск,
одновременные клики создания CV, содержимое PDF/DOCX, чужое скачивание 404, личная
переписка, повтор и удаление выбранного документа. Исполнитель E2E-сервера пока
последовательный; конкурентное выполнение документов проверяет backend integration.
Исторический E2E дополнен генерацией из прежнего запуска и проверкой его манифеста.
Все прежние factual/visual/refusal, API, импортные и QA-регрессии сохраняются.

Измеренные результаты полного gate находятся в [verification.md](verification.md).
Живой OpenAI и внешние источники в этом этапе не вызывались. Общие исполнители,
scheduler, квоты и журнал всех ролей добавлены на [этапе 7](shared-runtime.md).
Рабочая установка не переключалась.
