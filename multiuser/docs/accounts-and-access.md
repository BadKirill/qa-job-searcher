# Аккаунты, приглашения и доступ

Этап 3 переводит веб-приложение PostgreSQL на общий вход по логину и паролю.
Владелец каждого API-запроса определяется действующей сессией. Сервер создаёт
`CurrentUser` и персональный `PostgresStore` для этого запроса; параметры `user_id`,
заголовки клиента и роль администратора не заменяют владельца.

## Запуск на отдельной копии

Задать `DATABASE_URL`, `DATABASE_SCHEMA`, отдельные `WEB_DATA_DIR`, `WEB_ORIGINS`
и порт для репетиции. Применить миграции:

```bash
.venv/bin/python -m qa_job_bot.pg_database
```

Ревизия аккаунтов — `0003_accounts`. Она добавляет `auth_attempts` для ограничения
попыток входа/принятия ссылок и `created_by_id` для создателя приглашения/восстановления.
Для старых неиспользовавшихся токенов поле допускает NULL; новые выдачи записывают
ID администратора. Первые две ревизии не меняются.

Если база новая, создать единственного первого администратора:

```bash
.venv/bin/python -m qa_job_bot.legacy_cli bootstrap --login owner --display-name 'Владелец'
```

При переносе истории выполнить [проверку и импорт](legacy-import.md) до запуска
нового веб-приложения и выбора нового пароля. Импортированный scrypt-хеш продолжает
работать с логином, указанным при bootstrap. Рабочее переключение остаётся этапом 10.

```bash
.venv/bin/python -m qa_job_bot.web
```

При `DATABASE_URL` веб-сервер **не использует `WEB_OWNER_ID`**. Одна PostgreSQL
обслуживает разные сессии. На новой установке без старого пароля первоначальная
настройка доступна только единственному ещё не настроенному администратору по
приватному файлу `WEB_DATA_DIR/setup-token` (0600). Токен не возвращается через API.
Использование атомарно; повтор, включая одновременный запрос, пароль не меняет.
Публичной регистрации и назначения роли администратора через приглашение нет.

SQLite-режим прежней установки сохранён до рабочего переключения.
Вызов приложения с явно внедрённым `store` сохраняется для старых регрессий
и встроенных тестовых серверов. Сетевой entry point PostgreSQL выбирает только
общий режим с персональными сессиями. Указание одновременно store и database запрещено.

Промежуточный production worker пока требует явного `WEB_OWNER_ID` и обслуживает
этого владельца. Персональный scheduler, очередь всех пользователей, слоты и общий
API budget относятся к этапам 5–7. Наличие разных входов не означает готовность
параллельного worker. В browser fixtures используется отдельный последовательный
исполнитель синтетических задач разных владельцев; реальный OpenAI не вызывается.

## Вход и сессии

| Операция | Контракт |
| --- | --- |
| Состояние входа | `GET /api/session`: authenticated, setup_required, account_mode, csrf_token, минимальный user |
| Текущий пользователь | `GET /api/me`: id, login, display_name, role |
| Вход | `POST /api/login`: login, password |
| Первоначальная настройка | `POST /api/setup`: приватный token, password |
| Выход | `POST /api/logout` |
| Смена пароля | `POST /api/account/password`: current_password, password |
| Завершение всех сессий | `POST /api/account/sessions/revoke` |

Логин нормализуется NFKC, trim и casefold. Для новых приглашений допускается
3–100 букв/цифр и символов `. @ + - _`, имя — до 120 символов. Новые пароли —
12–256 символов; пароль хранится как scrypt-хеш прежнего совместимого формата.
Ошибка входа одинакова для отсутствующего, отключённого, ещё не активированного
аккаунта и неверного пароля. Для неизвестного аккаунта выполняется такой же
scrypt, чтобы не пропускать дорогую проверку. Изменение пароля/состояния между
проверкой и созданием сессии перепроверяется под блокировкой пользователя.

Cookie HttpOnly, SameSite=Strict, Secure для HTTPS-origin; серверный TTL — сутки.
В базе хранится SHA-256 токена сессии. CSRF обязателен для авторизованных мутаций,
Origin/Host проверяются и при входе/принятии ссылок. При новом входе токен cookie
меняется, прежняя сессия этого браузера удаляется. Смена пароля отзывает все старые
сессии и выдаёт новую текущему браузеру; старые reset-ссылки тоже отзываются.
Отзыв всех сессий завершает и текущую. Восстановление и отключение отзывают сессии;
включение аккаунта обратно не восстанавливает старые cookie.

Ограничения: 10 попыток на нормализованную идентичность/операцию и 60 на IP за
15 минут. Неизвестные логины и недействительные токены также учитываются. Проверка
и запись счётчиков сериализованы PostgreSQL advisory lock; счётчик действует между
процессами и перезапусками. В базе используются хеши логина/токена и IP, без сырых
секретов. IP берётся из peer соединения; произвольным X-Forwarded-For приложение
не доверяет. Конфигурация доверенного reverse proxy проверяется при развёртывании.

## Приглашения и восстановление

В разделе «Аккаунт и доступ» администратор задаёт логин и имя, получает одноразовую
ссылку и передаёт её адресату. Отправки email сервисом нет. При выдаче резервируется
пустой аккаунт без пароля, личных источников, фильтров, резюме и чужих результатов.
При принятии задаётся пароль и появляется персональная сессия.

| Операция | Контракт |
| --- | --- |
| Метаданные аккаунтов | `GET /api/admin/users` |
| Новое приглашение | `POST /api/admin/invitations`: login, display_name |
| Список приглашений | `GET /api/admin/invitations`: ID, адресат, срок, использование/отзыв; без секрета и хеша |
| Повторная выдача | `POST /api/admin/users/{id}/invitations` только для ожидающего аккаунта |
| Отзыв приглашения | `DELETE /api/admin/invitations/{id}` |
| Принятие | `POST /api/invitations/accept`: token, password |
| Выдача восстановления | `POST /api/admin/users/{id}/password-resets` только для активированного аккаунта |
| Отзыв восстановления | `DELETE /api/admin/password-resets/{id}` |
| Завершение восстановления | `POST /api/password-resets/accept`: token, password; затем обычный вход |
| Отключение/включение | `PATCH /api/admin/users/{id}`: disabled |

Приглашение действует 48 часов, восстановление — час. Повторная выдача отзывает
предыдущую неиспользованную ссылку. Отключение отзывает обе категории ссылок.
Владелец токена блокируется перед проверкой/использованием; одновременное принятие
не создаёт две сессии или два пароля. TTL проверяется повторно при атомарном
использовании, равенство времени истечения уже означает отказ. Недействительный,
просроченный, использованный и отозванный токен получают один ответ 403 без логина
и персональных данных. Отдельного публичного endpoint с данными адресата нет.

Секрет возвращается только при выдаче, хранится в базе только его SHA-256.
Ссылка использует `/#invite=...` или `/#reset=...`: фрагмент не уходит веб-серверу
в URL. Интерфейс переносит его в память формы и убирает из адресной строки.
Переходы по новым ссылкам в уже открытой вкладке обновляют форму и её токен.
Секреты не сохраняются в localStorage и не добавляются в wiki/логи.

Администратор видит минимальный реестр доступа, а не чужие профили, диалоги,
CV или документы. Нельзя отключить свой аккаунт. Новому пользователю нельзя
передать role/admin, owner_id или user_id в body для повышения прав: лишние
поля отклоняются. Прямой URL и угаданный ID чужого объекта возвращают 404.

## Разделение пространства и SSE

Все персональные операции получают хранилище только для текущего пользователя:
выдача/snapshot, Applied/архив, шаблоны, исходный PDF, страницы, повторный разбор,
активация, диалоги, задачи, проверенный текст, preview, скачивание, отмена и удаление.
Проверка владельца выполняется до файловой операции. Физические файлы пока находятся
в прежнем приватном корне с уникальными ID; дополнительное разделение каталогов
пользователя относится к этапу 6. Статический сервер их не публикует.

`/api/events` передаёт только revision владельца сессии. На каждом проходе
перепроверяются срок и действительность сессии/аккаунта. После logout, отзыва,
reset или отключения поток отправляет `session-ended` и завершается. React закрывает
старое пространство и запросы после проверки актуального cookie. При смене пароля
проверка ждёт завершения обновления cookie/CSRF, сохраняет действующую новую сессию
и открывает поток заново. Запоздавший ответ проверки не заменяет более новое состояние
аккаунта. При смене аккаунта Workspace получает новый ключ ID,
чтобы не сохранять старый профиль, выдачу, задачи и состояние форм.
Скачанные ранее данные невозможно отозвать; доступ к новому запросу проверяется
при его начале, поток событий — повторно во время работы.

## Проверки

Backend: реальные PostgreSQL-миграции, ограничения, атомарность и конкурентное
использование токенов, scrypt, сессии/CSRF/TTL, лимиты, отсутствие перечисления
логинов, смена пароля, административные права и creator, общий API с двумя
владельцами и без cookie. Отдельный тест перебирает все зарегистрированные
непубличные API-маршруты и проверяет 401 до разбора тела.

Frontend: login/invite/reset, смена пароля и CSRF, управление доступом и ошибки,
навигация по ссылкам внутри открытой вкладки, закрытие пространства по SSE.
Browser E2E: два приглашённых аккаунта в разных контекстах одного сервера,
пустое новое пространство, независимые результаты и PDF, отказ на чужие ID,
смена аккаунта, одноразовость/TTL/отзыв приглашений, пароль, reset, отключение и
отзыв всех сессий. Внешние ответы управляемые; PostgreSQL, API, рендер и браузер настоящие.
Фактические результаты полного gate фиксируются в [verification.md](verification.md).
