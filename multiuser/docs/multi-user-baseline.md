# Исходное состояние перед личными кабинетами

Дата: 11 ноября 2026 года, Europe/Belgrade. Этап 0
[плана разработки](multi-user-development-plan.md). Исходный commit:
`d9704bbc7f1d31cfb3883bd9e84931d4f4a439ff`; документация плана уже присутствовала
в рабочем дереве. Инвентаризация относится к доступной облачной копии проекта,
а не автоматически к рабочей установке владельца.

## Приложение и данные, которые предстоит разделить

FastAPI отдаёт React-интерфейс и API с одного origin. Единственный пароль создаётся
через setup-token; cookie-сессия и CSRF подтверждают вход, но не идентифицируют
отдельного человека. Два вошедших браузера используют одно пространство.

Настройки поиска читаются из трёх TOML-файлов. В текущей конфигурации 27 карьерных
досок: 14 Greenhouse, 9 Ashby, 4 Lever; также 13 публичных Telegram-каналов.
Пять агрегаторов добавляются фабрикой источников без персонального включения.

Долгие операции сохраняются в SQLite. Worker атомарно захватывает задание,
выполняет поиск/чат/документ и сохраняет результат; его основной цикл обрабатывает
одну задачу за раз. Сбор отдельных источников уже асинхронный. Время планового поиска,
его результат, ошибки и revision общие для всех сессий.

Профиль CV, подтверждённые факты, draft/active-версии, диалоги и сообщения
сохраняются в JSON payload таблиц. Генерация фиксирует входной контекст и проходит
фактическую и визуальную проверки. Эти данные сейчас не имеют отдельных владельцев.
Файлы находятся под `data/templates` и `data/artifacts/{task_id}` и выдаются через API.

### Схема SQLite

| Таблицы | Идентификаторы и состояние | Изменение следующей версии |
| --- | --- | --- |
| `jobs`, `job_identities` | fingerprint, внешний source key, payload с персональными score и match_reasons | Разделить содержание и оценку пользователя |
| `subscriptions`, `deliveries` | chat_id и fingerprint | Сохранить историю и явно привязать Telegram к аккаунту |
| `web_settings` | Общие настройки, пароль, current_jobs, revision и расписание | Отделить системные настройки от персональных |
| `web_state` | Единственная строка по job_id, applied_at/archived_at | Ключ пользователь–вакансия |
| `web_snapshots` | UUID, список ID, время | Добавить владельца и версии поиска |
| `web_templates` | UUID, draft/active/retired, payload | Активный эталон отдельно на человека |
| `web_conversations`, `web_messages` | UUID, глобальный уникальный scope; request ID внутри диалога | Персональный scope и проверка связанных владельцев |
| `web_tasks`, `web_task_requests` | UUID, глобальные request ID/scope, payload/result, lease | Персональная идемпотентность и несколько исполнителей |
| `web_artifacts` | UUID задачи, путь и хеши в payload | Владелец, составная связь с задачей, персональная выдача |
| `web_sessions`, `web_login_attempts` | Хеш токена/CSRF/expiry; попытки по IP | Пользователь в сессии, лимиты по аккаунту и IP |
| `schema_migrations` | Применены версии 1, 2 и 3 | Целевые версионированные миграции PostgreSQL |

В доступной копии: 0 вакансий, идентичностей, доставок, подписок, статусов,
снимков, шаблонов, диалогов, сообщений, артефактов и сессий. Есть 5 записей настроек,
1 задание и 1 запись идемпотентности. Значения настроек, токены и содержимое задач
в инвентаризацию не выводились. Резюме и сгенерированных PDF/DOCX в этой копии нет.
Перенос реальной рабочей истории данным аудитом не проверен.

Существующие fingerprints должны сохраняться. Источник идентифицируется по
source/source_id или URL; одинаковое название/компания/география не должны
переносить статусы и документы на другое объявление. Applied и архив независимы;
при обоих признаках отображение в архиве имеет приоритет.

## Возможности девяти типов источников

Матрица основана на текущем коде адаптеров и контрактных тестах. Она не является
отчётом о доступности живых площадок или гарантии полноты их API.

| Источник | Получение и описание | Существующее ограничение | Работа для личного поиска |
| --- | --- | --- | --- |
| Remotive | Общий `/api/remote-jobs`, текст description, без обхода страниц | Доступное окно remote-фида; персональных параметров нет | Собственное включение, локальный отбор и честная свежесть |
| Himalayas | Search API, восемь QA-запросов, только page 1; description или excerpt | Только QA-запросы; часть географии вне Europe/CIS отбрасывается, исходные ограничения сокращаются | Запросы из профиля, пагинация по возможностям API, сохранение полного набора ограничений |
| We Work Remotely | Общий RSS, текст description, без пагинации | Ограниченное окно RSS, неполная география возможна | Свой выбор источника, универсальный matching и отметки неполноты |
| Remote.com | Восемь QA-запросов с page_size 100, затем detail API | Дополнительный QA-title отбор до detail, без обхода следующих страниц | Профильные запросы и detail без обязательного QA-фильтра |
| Hirify | Страницы 1–3, описание/tldr/stack | `qa_testing` и `remote` зашиты; география может сокращаться до Europe/CIS | Поддерживаемые категории/форматы из профиля, полные исходные ограничения |
| Greenhouse | Список доски и detail для выбранных объявлений | QA-title отбор перед запросом деталей | Все подходящие роли профиля; контролируемый объём detail-запросов |
| Lever | Список доски, global/eu endpoint; основной текст, lists и additional | Получение доски целиком без пользовательских параметров | Своя доска/регион и локальный универсальный отбор |
| Ashby | Job board API с compensation, description plain/html, secondary locations | Только перечисленные доски; `isListed=false` пропускается | Своя доска и локальный профиль; сохранить ограничения публикации |
| Публичные Telegram-каналы | HTML preview последней и предыдущей страницы, текст поста | Выделение заголовка по QA-pattern, окно двух страниц и эвристическая география | Свой канал, названия ролей из профиля, явная ограниченность окна |

Личная база источников первой версии означает собственные подключения поддерживаемых
публичных типов. Произвольные сайты и источники с входом в аккаунт не становятся
работающими коннекторами после добавления URL. Изменение сетевых разрешений окружения
проверяется отдельно от сохранения источника в UI.

## Зафиксированные регрессии и будущие изменения

Общий набор `tests/fixtures/search-baseline.json` содержит три синтетических профиля
и десять вакансий. Поле `baseline` — проверенное поведение существующей реализации;
`target` — поведение после персонализации. Будущие ожидания не подменяют результат
текущих тестов и не оформляются как пропущенные/xfail проверки.

При реализации персонального matching на этапе 4 проверки изменяемых сценариев
переключаются на `target`; `baseline` остаётся историческим свидетельством исходного
поведения. Неизменённые сценарии владельца продолжают проверяться без ослабления.

| Сценарий | Сейчас | Требование после персонализации |
| --- | --- | --- |
| Middle Manual QA, Europe | Принимается, Manual-фокус даёт бонус | Сохранить в профиле владельца |
| Senior QA, Serbia hybrid | Принимается | Сохранить в профиле владельца |
| Junior QA в профиле владельца | Отклоняется | Сохранить в профиле владельца |
| Europe с явным Germany-only в описании | Отклоняется для профиля владельца | Сохранить ограничение кандидата |
| Senior Backend Engineer с явными role_keywords | Принимается при прямой настройке SearchProfile | Настройка через кабинет и поддержка адаптерами |
| Junior Backend Engineer с пустыми исключениями | Отклоняется из-за глобального Junior-pattern | Разрешить, когда профиль допускает Junior |
| QA Engineer при поиске только Backend Engineer | Принимается через встроенный QA fallback | Отклонить как чужую роль |
| Senior Product Designer, Europe | Принимается при прямой настройке SearchProfile | Настройка через кабинет и поддержка адаптерами |
| Product Designer, Berlin hybrid, Berlin разрешён | Отклоняется из-за правила Serbia hybrid | Разрешить выбранный hybrid/географию |
| Product Designer, Berlin onsite, require_remote=false | Принимается при прямой настройке SearchProfile | Сохранить возможность явного выбора формата |

Существующий matching умеет находить произвольную роль через явно заданный
`role_keywords`; универсальному поиску мешают общая конфигурация, QA fallback,
предварительная фильтрация адаптеров и жёсткие правила уровня/географии.
Переписывать весь механизм, предполагая полное отсутствие такой возможности, не нужно.

Дополнительно обнаружены персональные данные в общей записи Job, изменение Job
при ранжировании, глобальные revision/scope/request ID, кэшированный общий search
в worker и изменяемый `AgentGateway.last_run_metadata`. Их нужно разделить до
включения нескольких исполнителей и до допуска второго рабочего пользователя.

## Проверки первого этапа

Добавлены unit-проверки matching по десяти сценариям, три интеграционных пути
SearchService → SQLite → повторное открытие → авторизованный API → Applied,
шесть frontend component-проверок карточек разных направлений и отдельный браузерный
сценарий matching → хранилище → API → React → архив → reload → восстановление → logout.
Существующие browser E2E документов выполняются дополнительно.

Браузерный baseline использует отдельный временный сервер на порту 8012;
существующие E2E — порт 8011. Это два тестовых набора одного текущего приложения,
а не реализация двух личных кабинетов. Тестовые данные всех профессий в baseline
публикуются в одном пространстве намеренно; проверка разделения аккаунтов появится
вместе с аккаунтами. Внешние источники и OpenAI заменены управляемыми ответами;
API, SQLite, worker, рендер и браузер используются настоящие.

Первый запуск quality gate: 806 backend и 66 frontend тестов прошли, E2E не стартовали
из-за отсутствующего Playwright Chromium. Попытка установки в стандартный cache
также не прошла из-за недоступного пути домашнего каталога. Браузер установлен
в разрешённый `/workspace/qa-tools/ms-playwright`; дальнейшие прогоны используют
`PLAYWRIGHT_BROWSERS_PATH`. Итоговые измерения приведены в
[журнале проверок](verification.md).
