# Общие исполнители, расписание и квоты

Этап 7 [плана личных кабинетов](multi-user-development-plan.md).
API, исполнители и планировщик используют одну PostgreSQL. Общий серверный
OpenAI-проект и ключ сохраняются; браузер их не получает.

## Запуск на подготовленной копии

Установить зависимости и проект по [инструкции запуска](running-web.md), задать
`DATABASE_URL`, при необходимости `DATABASE_SCHEMA`, `WEB_DATA_DIR`, `WEB_ORIGINS`
и собрать frontend. Ключ и сохранённый агент настраиваются прежним серверным способом.
Значения секретов не передаются через UI лимитов и не записываются в команды ниже.

```bash
.venv/bin/python -m qa_job_bot.pg_database
```

После миграций запустить в отдельных процессах:

```bash
.venv/bin/python -m qa_job_bot.web
```

```bash
.venv/bin/python -m qa_job_bot.worker
```

```bash
.venv/bin/python -m qa_job_bot.scheduler
```

При `DATABASE_URL` worker обслуживает все активированные аккаунты; `WEB_OWNER_ID`
ему больше не нужен. По умолчанию процесс запускает по два асинхронных исполнителя
поиска, чата и документов. Несколько таких процессов могут работать с одной БД.
Чтобы выделить группу в отдельный процесс, задать `WORKER_LANE=search`, `chat`
или `document`; значение `all` используется по умолчанию. В каждой выбранной группе
процесс содержит два исполнителя; повышение лимита в БД само не добавляет процессы.

Планировщик — отдельная команда `qa-job-scheduler` после установки новой версии
пакета, либо показанный Python-модуль. Запуск только API не исполняет очередь;
запуск только worker не включает автоматическое расписание PostgreSQL.
Старый standalone SQLite worker сохранён для совместимости и регрессий.
Привязанные команды Telegram/импорта могут по-прежнему требовать владельца.
Рабочее переключение и настройка автозапуска относятся к заключительному этапу.

## Очередь и слоты

| Настройка | Стартовое значение | Область |
| --- | --- | --- |
| Одновременные поиски | 2 | Вся платформа |
| Одновременные чаты | 2 | Вся платформа |
| Одновременные документы | 2 | Вся платформа, CV и письма вместе |
| Документы пользователя | 1 | Один аккаунт |
| Поиск/чат пользователя | По одному каждого вида | Один аккаунт |
| Одновременные OpenAI-вызовы | 2 | Вся платформа, все роли |
| OpenAI-вызовы пользователя | 1 | Один аккаунт, включая неопределённый исход до окончания резерва |
| API-вызовы за сутки | 600 | Вся платформа |
| API-вызовы пользователя за сутки | 60 | По умолчанию, индивидуально меняются администратором |

Числа — изменяемые технические настройки для первого пилота, не обещание
пропускной способности и не денежный бюджет. Стартовые пределы выбраны без изменения
лимитов самого OpenAI-проекта. Их соответствие реальным лимитам проверяется до пилота.

`runtime_control` сериализует короткие транзакции выбора и резервирования. Выбор
очередного пользователя учитывает последний захват в своей группе; затем выбирается
его старейшая подходящая задача с `FOR UPDATE SKIP LOCKED`. Глобальные и персональные
слоты проверяются в той же транзакции. Сеть и рендер выполняются после её завершения.
Поток поисков не занимает документные слоты. Лимиты действуют суммарно между процессами.

Каждый захват получает новый execution/worker UUID. Lease общего worker — 90 секунд,
heartbeat — каждые 15 секунд. Heartbeat проверяет владельца исполнения, статус,
неистёкший lease и активный аккаунт. Он не оживляет просроченный захват.
Завершение, публикация поиска и регистрация файлов используют действующий lease
и execution ID; поздний старый исполнитель не перезаписывает новый результат.

Истёкший персональный поиск с закреплёнными входами можно безопасно захватить заново,
максимум до трёх захватов. Старое задание без закреплённых входов получает отказ.
Истёкшие чат/CV/письмо автоматически заново не отправляются: возможный платный
запрос уже мог попасть к провайдеру. Пользователь видит отказ и сам решает повторить
операцию; новый запрос всё равно проходит квоту и защиту неопределённого API-слота.

Отмена или отключение аккаунта прекращают продление lease. Исполнение отменяется
на ближайшем heartbeat; транспорт пытается отменить известную внешнюю сессию.
Нативный рендер в thread может закончиться позже, но его файлы не регистрируются
и не выдаются. Отключение аккаунта также атомарно переводит его queued/active задания
в cancelled и отзывает сессии. Аккаунты без завершённой активации не получают новые
задания в общем worker.

## Персональное расписание

В «Аккаунт и доступ» → «Расписание и лимиты» пользователь включает автоматический
поиск и выбирает интервал 15–1440 минут. По умолчанию — 180 минут. Сохранение
переносит следующий запуск на выбранный интервал от текущего времени.

Первое расписание создаётся с устойчивым смещением по SHA-256 user ID в диапазоне
1–10800 секунд, чтобы новые кабинеты не запускались одновременно. По умолчанию оно
включено, но выполнение требует подтверждённого входа, настроенного профиля и
включённых корректных источников. Ненастроенный аккаунт пропускает этот срок.
Повтор после пропущенных интервалов создаёт один поиск и переносит дату вперёд,
а не догоняет все пропущенные запуски.

Постановка поиска, request ID срока и продвижение расписания находятся в одной
транзакции с блокировкой аккаунта. Несколько планировщиков не создают дубль.
Активный поиск тех же версий объединяется действующим механизмом идемпотентности.
Существующие настройки и выбранные вакансии не меняются из-за самого расписания.

## Резервы и журнал OpenAI

`MeteredGateway` используется общим runtime для генератора, factual reviewer,
visual reviewer, исправлений и чатов. Он резервирует одну единицу суточной квоты
и API-слот до вызова. При занятых слотах или общем cooldown он ждёт, не выполняя
нового платного POST. Ожидание ограничено 240 секундами, общий deadline задания
сохраняется 840 секунд. Поиск публичных источников эту квоту не расходует.

Отдельный `CALL_AUDIT` ContextVar связывает транспортные события с конкретным
резервом, без общего изменяемого last-call состояния. До POST фиксируется отправка;
полученные session/turn IDs сохраняются сразу. Usage записывается до проверки
конечного JSON, поэтому ошибка ответа не скрывает уже известный расход.

| Состояние резерва | Значение |
| --- | --- |
| reserved | Квота и слот зарезервированы, отправка ещё не подтверждена локально |
| sent | Запрос мог попасть к провайдеру |
| completed | Вызов вернулся успешно; отрицательный вердикт reviewer тоже является выполненным вызовом |
| failed | Провайдерный turn закончен либо получен явный окончательный 429, но вызов не дал пригодного ответа |
| unknown | После отправки исход не установлен; единица квоты сохранена |
| released | Отказ до отправки; единица возвращена |

Резерв отправленного вызова с неизвестным исходом продолжает занимать API-слот
до исходного 300-секундного срока. Он не освобождается немедленно после timeout.
Умерший процесс оставляет журнал; reaper завершает истёкший reserved как released,
а sent как unknown и создаёт usage event. Поздняя попытка отправить уже освобождённый
резерв отклоняется. Подтверждённый конечный turn освобождает слот сразу.

В `usage_reservations` и `usage_events` хранятся владелец, task ID, роль, резерв,
состояние, день UTC, execution ID, доступные внешние ID и usage. Unknown usage —
`null`, не ноль. Повтор завершения не добавляет второй event. Суточный счётчик
учитывает все незавершённые/отправленные/завершённые/неопределённые попытки, кроме
released. Удаление документа оставляет финансовый журнал и не обнуляет лимит.
Новый request ID не обходит суточный предел. Повтор исходного request ID возвращает
прежнюю задачу и не запускает её второй раз.

Показатель токенов суммирует только известные целые счётчики провайдера; рядом
показано число вызовов без точного usage. Квота ограничивает число вызовов, а не
токены или деньги. Отдельного расчёта стоимости и автоматической сверки неизвестных
сессий с биллингом пока нет; точный счёт остаётся у провайдера. Внешние ID доступны
оператору в БД для сверки, пользовательский API не открывает чужое содержание.

## Ошибки и административные изменения

Только явный 429 повторяется автоматически: максимум три HTTP-попытки с тем же
Idempotency-Key. Числовой и HTTP-date Retry-After учитываются. Пауза до 60 секунд
ожидается внутри вызова; более длинная сохраняется как общий cooldown и завершает
вызов без раннего повтора. Все исполнители читают этот cooldown перед новым резервом.
Неоднозначный POST timeout, сетевой разрыв и 5xx автоматически заново не отправляются.
Отмена известной сессии выполняется с отдельным ограниченным ожиданием.

Администратор в тех же настройках меняет общие суточные/стартовые лимиты, число
одновременных вызовов и персональную суточную квоту. Нулевой лимит запрещает новые
API-вызовы. Снижение не отменяет уже принятые провайдером вызовы; следующие роли
документа снова проверяют предел. Например, нехватка квоты на visual review блокирует
выдачу, даже если генератор и factual reviewer уже успешно завершились.

## API и миграция

| Маршрут | Доступ |
| --- | --- |
| `GET /api/usage` | Только свой день UTC, лимит, вызовы, известные токены, unknown count и общий cooldown |
| `GET /api/schedule` | Только собственное расписание |
| `PUT /api/schedule` | Собственные enabled/interval_seconds; произвольный user_id запрещён |
| `GET /api/admin/runtime` | Администратор: общие лимиты и сводки квот аккаунтов |
| `PUT /api/admin/runtime` | Администратор: валидированные общие настройки |
| `PUT /api/admin/users/{id}/limits` | Администратор: daily_calls конкретного аккаунта |

Сохраняются Origin/CSRF, сессии, запрет дополнительных полей и валидация чисел.
Приватный CV, диалог или документ не раскрываются административной сводкой квоты.

Ревизия `0007_shared_runtime` добавляет runtime_control и search_schedules, индексы
журнала и идемпотентность финального usage event. Прежние шесть SQL-ревизий не меняются.
Upgrade/downgrade проверяют сохранение эталона и вакансии. Downgrade удаляет настройки
нового runtime/расписаний; перед эксплуатационным откатом нужна резервная копия.

## Проверки и границы

Unit/API/integration используют настоящую PostgreSQL. Несколько отдельных процессов
конкурируют за документные и API-слоты; проверяются справедливость, heartbeat,
перехват безопасного поиска, отказ позднего worker, отмена внутри рендера, дневные
пределы, неизвестный расход, идентификаторы, роли и атомарность расписания. Настоящий
MCP stdio и OpenAITransport с управляемым HTTP проверяют сохранение usage как при
успехе, так и при невалидном финальном ответе.

Frontend unit проверяют личные и административные формы, отсутствие чужих настроек,
сохранение, ошибку без потери черновика и запоздавшие ответы. Browser E2E проходит
нулевую квоту → отказ без API-вызова → увеличение → готовый CV с тремя учтёнными ролями,
личное расписание/reload и запрет административной операции обычному пользователю.
Account E2E-сервер использует общий RuntimeWorker и его metering с fixture gateway.

Результаты полного gate — в [verification.md](verification.md). Живой OpenAI,
внешние источники и фактические лимиты провайдера в этом этапе не проверяются
управляемыми ответами. Нагрузочный пилот на 10–20 человек, provider smoke/eval,
мониторинг, восстановление из резервной копии и рабочее переключение ещё впереди.
Оставшиеся приватные файлы незавершённого нативного рендера автоматически не убираются.
