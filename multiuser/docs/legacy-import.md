# Перенос SQLite и приватных файлов в PostgreSQL

Этап 2 добавляет автономную репетицию переноса. Рабочее переключение остаётся
этапом 10. Общий вход по приглашениям реализован на этапе 3: [аккаунты и доступ](accounts-and-access.md).
Импорт не обращается к источникам, Telegram или OpenAI и не запускает worker.

## Подготовка

Для согласованности базы и файлов остановить процессы **копируемой установки**:
API, worker и Telegram-бот. SQLite backup API даёт согласованный снимок базы,
включая WAL, но не блокирует изменение или удаление файлов другими процессами.
Поддержка онлайн-копирования одновременно изменяемой базы и файлов не заявляется.
На этапе разработки использовать отдельную копию; рабочую установку не переключать.

Проверить свободное место, права и отдельную тестовую PostgreSQL. Снимок содержит
приватные данные, в том числе старые диалоги, исходный CV и хеш пароля. Хранить его
вне репозитория и frontend, не прикладывать к CI, issue или публичной документации.
Копии и файлы создаются с правами 0700 для каталогов и 0600 для файлов.
Промежуточные каталоги снимка и переносимых файлов также создаются с правами 0700
независимо от исходной umask оператора.

Предварительно установить зависимости и применить миграции к целевой базе:

```bash
.venv/bin/python -m qa_job_bot.pg_database
```

Подключение задают `DATABASE_URL` и `DATABASE_SCHEMA`; не передавать секреты
в аргументах CLI. Ревизия импорта — `0002_legacy_import`: к исходной модели добавлены
персональные `legacy_records` и составная уникальность журнала `import_runs`.
Первая ревизия не переписывается; upgrade/downgrade второй также фиксированы SQL.

## Создание снимка

Пути ниже — пример для отдельной репетиции. `--data-dir` должен содержать
`templates/` и `artifacts/` копируемой установки; `--config-dir` — её три TOML-файла.

```bash
.venv/bin/python -m qa_job_bot.legacy_cli snapshot \
  --database /srv/job-searcher-copy/data/jobs.sqlite3 \
  --data-dir /srv/job-searcher-copy/data \
  --config-dir /srv/job-searcher-copy/config \
  --output /srv/job-searcher-rehearsal/snapshot-20261111 \
  --legacy-data-root /srv/job-searcher/data
```

`--legacy-data-root` — прежний абсолютный корень путей, записанных в JSON.
Он нужен, если копия файлов уже перемещена. Без него используется абсолютный
`--data-dir`. Относительные пути вида `data/templates/...` поддерживаются, если
`data` — имя прежнего корня. Произвольные внешние пути и `..` запрещены.

Команда не изменяет таблицы или файлы источника. Backup SQLite переводится в
автономный DELETE journal mode; для чтения проверенных байтов используется
SQLite в памяти. Поддерживаются ранние jobs без payload и веб-схемы версий 1–3.
Неизвестные таблицы, views, virtual tables, неизвестные столбцы и повреждение
структуры останавливают перенос. В снимок входят:

- `legacy.sqlite3`, проверенная через `integrity_check`;
- все обычные файлы `templates/` и `artifacts/`, включая промежуточные;
- `search_profile.toml`, `job_boards.toml`, `telegram_channels.toml`;
- `manifest.json` с количеством/размером, SHA-256 файлов, базы и логических строк.

`.env`, setup-token, логи и произвольные файлы корня не копируются.
Символические ссылки и специальные файлы запрещены, чтение выполняется через
дескрипторы каталогов с `O_NOFOLLOW`. Ограничения: 64 MiB на приватный файл,
256 MiB на SQLite, 512 MiB на содержимое снимка, 10000 приватных файлов,
1 MiB на исходный TOML. Если история больше, лимиты нужно отдельно пересмотреть
и проверить до переноса; автоматического обрезания данных нет.

## Владелец и предварительная проверка

В полностью новой PostgreSQL создать первого администратора:

```bash
.venv/bin/python -m qa_job_bot.legacy_cli bootstrap \
  --login owner --display-name 'Владелец'
```

Bootstrap под блокировкой таблицы допускается только при отсутствии аккаунтов.
Он возвращает ID, не выдаёт пароль и не открывает публичную регистрацию.
Без старого пароля новая установка использует существующий приватный web setup-token.
Если аккаунт уже создан на этапе 1, использовать его ID; повторный bootstrap запрещён.
Аккаунт импорта должен быть активен и не содержать пользовательских данных.
Существующий пароль должен отсутствовать или точно совпадать со старым хешем.

```bash
.venv/bin/python -m qa_job_bot.legacy_cli check \
  --snapshot /srv/job-searcher-rehearsal/snapshot-20261111 \
  --owner-id '<явный ID владельца>' \
  --target-dir /srv/job-searcher-rehearsal/restored-data \
  --telegram-chat 123456789
```

`--telegram-chat` повторяется для каждого **проверенного** chat ID владельца.
Аргумент необязателен: без него ни один чат автоматически не привязывается.
Неизвестный для исходной истории ID отклоняется. Неактивная подписка сохраняет
неактивность; доставки с неизвестной вакансией остаются в архиве без активной связи.

`check` проверяет манифест, файлы, ссылки, доказательства документов и конфигурацию,
выполняет пробную запись в настоящую PostgreSQL внутри откатываемого savepoint
и сверяет значения. Данные и файлы назначения не публикуются. PostgreSQL может
продвинуть sequence сообщений; непрерывность sequence не требуется.
Успешная проверка не резервирует состояние базы для более позднего `restore`.

## Импорт и проверка результата

```bash
.venv/bin/python -m qa_job_bot.legacy_cli restore \
  --snapshot /srv/job-searcher-rehearsal/snapshot-20261111 \
  --owner-id '<тот же ID владельца>' \
  --target-dir /srv/job-searcher-rehearsal/restored-data \
  --telegram-chat 123456789
```

Назначение должно быть новым каталогом вне снимка. Нельзя направлять импорт
на существующий рабочий `WEB_DATA_DIR` или смешивать чужие файлы. Сначала
формируются приватные staging-файлы рядом с назначением, проверяются хеши,
затем пишутся строки одной транзакцией PostgreSQL. Файлы публикуются rename
в пределах той же файловой системы; содержимое и каталоги синхронизируются.
Глобальная advisory lock сериализует импорты, строка владельца блокируется.

Отчёт JSON содержит source hash, исходные/ожидаемые/проверенные количества,
контрольные суммы и размеры файлов, проблемы по кодам/ID, неполные вакансии,
число непривязанных Telegram-записей, отменённых сессий и повторно использованных
публичных вакансий. CV, тексты диалогов, пароль/хеш и DSN в отчёт не выводятся.
Полное соответствие путей и хешей остаётся в приватных манифестах.

| Данные | Поведение переноса |
| --- | --- |
| ID, fingerprints, внешние source keys | Сохраняются; конфликт с другой историей отклоняется |
| Даты, Applied, архив, снимки, сообщения | Сохраняются с исходным порядком сообщений |
| Score, причины, географическая оценка | Отдельные личные записи выбранного владельца |
| Неполные старые вакансии | `needs_refresh`, пустое описание без выдуманного текста; не добавляются в свежую выдачу, Applied/архив сохраняются |
| Генерация по неполной вакансии | Заблокирована в интерфейсе и API (409) до обновления содержания |
| Шаблоны, facts, reference, pinned context | Сохраняются; меняются только известные файловые пути и явный owner ID контекста |
| Готовые документы | Только при валидных старых content/visual review, draft/template/file hashes и совпадающих artifact IDs |
| Недостаточные доказательства | Документ становится `blocked`; исходный result и файлы сохраняются приватно, скачивание запрещено |
| Running/verifying/rendering | `failed`, исход выполнения неизвестен; автоматического повторного платного вызова нет |
| Queued | Сохраняются ID и request ID; дубли scope и неполный контекст блокируются |
| Пароль | Исходный scrypt-хеш переносится без смены пароля |
| Сессии | Исходные не импортируются; прежние сессии целевого владельца отменяются, другие владельцы не затрагиваются |
| TOML | Версия личного профиля и личные источники; исходные файлы сохраняются приватно |
| Неизвестные Telegram-связи | `legacy_records`, `linked=false`; без активной подписки/доставки |

Исторические строки с разными fingerprints и одним source key сохраняются как
отдельные вакансии, если исходная `job_identities` явно выбирает одну из этих строк,
а source key и URL выбранной и исторической строк совпадают. В отчёте каждая
историческая строка отмечается `historical_identity_alias`. Её Applied, архив,
документы и исходный ID не объединяются с выбранной строкой. При отсутствии
явного выбора, другом URL, несовпадающем source key или отсутствующей выбранной
строке импорт останавливается с `identity_conflict`.

Импорт не создаёт новые одобрения документов и не запускает повторную проверку моделью.
Исходные payload вакансий, шаблонов и заданий, а также Telegram-записи сохраняются
в персональном архиве `legacy_records` для сверки. Полный исходный снимок сохраняется.
Одинаковая уже существующая публичная запись может использоваться совместно;
отличающаяся запись не перезаписывается. Чужие личные данные не изменяются.

Персональный профиль и источники на этом этапе **сохранены в PostgreSQL**.
Чтение их поисковым pipeline вместо прежнего TOML относится к этапам 4–5;
пользовательское управление Telegram-привязками — к этапу 9.

## Повтор и восстановление после прерывания

Повторить **ту же** команду `restore` с тем же снимком, владельцем, назначением
и набором Telegram chat ID. Стабильный source hash не зависит от времени создания
снимка. После успешного переноса проверяются файлы и возвращается
`already_imported=true`; новые изменения пользователя и новые сессии не сбрасываются.
Смена владельца, каталога, связей чатов, манифеста или файлов отклоняется.

PostgreSQL и файловая система не имеют общей распределённой транзакции:

- До rename незавершённая транзакция не публикует данные; обычная ошибка убирает staging.
- При ошибке внутри записи после rename, до начала commit, база откатывается,
  опубликованный новым импортом каталог удаляется после сверки его манифеста.
- При потере подтверждения commit возвращается `commit_outcome_unknown`.
  Файлы сохраняются: база могла уже зафиксировать строки. Повтор той же команды
  сверяет журнал и безопасно обрабатывает оба исхода, без удаления нужных файлов.
- При жёстком завершении процесса после rename до commit каталог может остаться,
  а транзакция PostgreSQL откатится. Совпадающий `import-manifest.json` и хеши позволяют
  той же команде безопасно завершить восстановление без новой оплаты или дублей.
- При завершении после commit журнал `import_runs` подтверждает импорт; повтор проверяет
  файлы и возвращает прежний отчёт.
- Оставшийся после жёсткого сбоя скрытый `.restored-data.import-*` не используется
  приложением. Удалять его вручную только после остановки импорта и проверки пути.
  Не удалять несогласованный каталог назначения для обхода ошибки.

До проверки результата не запускать приложение/worker с этим назначением.
Для отдельной ручной репетиции задать `WEB_OWNER_ID` выбранного аккаунта,
`WEB_DATA_DIR` нового каталога и отдельные порт/origin. Старые cookie не подходят;
проверить вход старым паролем, Applied, архив, профиль, диалоги, оригинал и скачивание
проверенных документов. Политика автоматического поиска worker остаётся прежней;
не запускать его с реальным ключом ради проверки миграции.
