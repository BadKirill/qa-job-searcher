# Переключение и закрытый пилот

15 ноября 2026, Europe/Belgrade. Техническая подготовка этапа 10 и рабочий
импорт на Mac выполнены; новый Docker/PostgreSQL runtime работает на прежнем
адресе. Владелец завершил настройку, второму участнику создано приглашение.
Активация участника и реальная проверка пары ещё ожидаются, лимит остаётся 2.
Отчёт локального переключения — в `verification.md`.
Пароли и значения ключей в чат не передаются.

## Что подготовлено

- Приватный `.maintenance` в `WEB_DATA_DIR`: API закрывается для чтения и записи,
  SSE завершает поток, браузер показывает обслуживание и убирает личное содержимое.
  Workers и scheduler не берут/не создают новые задания; оба Telegram-пути стоят.
- Пилот `pair`: владелец и один тестовый участник. Pending-приглашение резервирует
  место. Конкурентные приглашения и повторное включение аккаунта учитывают лимит.
- Переход в `cohort` на 20 мест требует полного отчёта двух активированных аккаунтов,
  совпадения владельца и source hash действительного импорта. Статус виден только
  администратору. В интерфейсе нет действия, которое само объявляет проверки пройденными.
- Фиксация границы импорта и проверка изменений перед возвратом к SQLite. Новые
  записи/файлы блокируют простой перезапуск старой версии; границу нельзя затереть
  повторной фиксацией после изменений.
- Browser E2E переносит синтетическую историю в отдельную PostgreSQL, проверяет
  старый пароль, историю, два кабинета и документа, приглашения, исходную SQLite
  и отказ простого отката после нового прогресса. Это репетиция, не рабочий пилот.

Порядок импорта и его ограничения: [legacy-import.md](legacy-import.md).
Сервисы, приватные volumes и recovery: [runtime-operations.md](runtime-operations.md).

## До остановки рабочей установки

1. Установить точный рабочий каталог и SQLite/data/config. Проверить, что это
   установка с реальной историей. Подготовить отдельный проверенный release,
   PostgreSQL и свободное место, сохранив прежние исходники/venv/конфигурацию.
   Использовать проверенное содержимое рабочего дерева или точный image digest:
   текущий Git HEAD не включает незакоммиченные изменения этапов разработки.
2. Установить фактический способ запуска API, worker, scheduler, Telegram и туннеля.
   Старый `deployment.py` описывает macOS/launchd и ngrok; это не подтверждает
   актуальные процессы или SSH-доступ. Не угадывать PID, label или рабочий каталог.
3. Заранее подготовить копию среды и способ вернуть прежний runtime. Новый хостинг
   этим этапом не создаётся. Существующий ngrok URL требует работающего хоста.
4. Проверить, где лежат действующие приватные OpenAI/Telegram настройки. Сохранить
   их отдельно в приватной операторской копии с хешами. Legacy snapshot копирует
   три TOML и приватные templates/artifacts; `.env`, ключи и ngrok-конфигурация
   автоматически в него не входят. Их не помещают в публичные отчёты.

## Обслуживание и остановка источника

Для версии, которая уже поддерживает флаг, на её хосте выполнить:

```bash
python -m qa_job_bot.maintenance on --data-dir /private/working-project/data
python -m qa_job_bot.maintenance status --data-dir /private/working-project/data
```

Пути здесь и ниже — примеры, их заменяют подтверждёнными рабочими путями.
Флаг — пустой каталог 0700. При повреждённом/недоступном marker обслуживание
остаётся включённым; CLI не удаляет чужой, публичный или не пустой marker.
`GET /api/session` возвращает только признак обслуживания и отсутствие авторизации,
остальные API — 503/Retry-After без доступа к данным. `/health/live` остаётся 200,
`/health/ready` становится 503. Статические файлы интерфейса доступны.

Флаг ограничивает новую работу, но не завершает уже начатую транзакцию или удалённый
OpenAI turn. После включения остановить фактические API/scheduler/workers/Telegram
и проверить остановку. Старые процессы, загруженные из версии без этой поддержки,
не читают новый marker: сначала закрыть внешний вход на proxy/туннеле и остановить
их средствами их реального service manager. Запись должна оставаться остановленной
до окончания копирования. Проверка пары хешей не заменяет остановку писателей.

Сверить active/running/verifying/rendering и известные session/turn IDs с проектом
OpenAI; сохранить приватные наблюдения о незавершённых вызовах. Неизвестный исход
сохраняется неизвестным, не становится нулевым расходом и не запускает повторную
платную генерацию. Импорт переводит незавершённые исполнения в failed, сохраняя
исходные данные и историю. Проверить и сохранить причины в отчёте импорта.

## Согласованный снимок и отдельное назначение

После остановки писателей выполнить `legacy_cli snapshot` через SQLite backup API,
затем `check` и `restore` по инструкции переноса. Хранить снимок приватно. Сверить
source counts/hash, files/hash, Applied, архив, CV, messages, документы и Telegram
records. Оригинальные SQLite и файлы остаются на месте; их не обнуляют и не заменяют.

Для Compose удобен отдельный leaf внутри нового volume:

```dotenv
WEB_DATA_DIR=/app/data/current
```

Volume монтируется в `/app/data`, а `/app/data/current` до импорта должен отсутствовать.
`legacy_cli restore --target-dir /app/data/current` публикует новый каталог. Если
создать его через API или marker до импорта, предварительная проверка назначения
откажет. Поэтому сначала запускают только PostgreSQL/migrate и bootstrap владельца,
затем импорт, и только после него — обслуживание целевого каталога.

Снимок подключают read-only с приватными правами, доступными пользователю импортера.
После копирования проверяют владельца 10001 и права 0700/0600 целевых файлов для
runtime image. Права исходных файлов не расширяют. Конкретную передачу snapshot и
UID подбирают по подтверждённому хосту; Docker/macOS и Linux могут различаться.
Старый процесс и новое назначение не используют одну изменяемую SQLite/data.

Bootstrap задаёт новый login владельца; старый пароль переносится в виде scrypt-хеша.
Пароль не сбрасывают для удобства миграции. Старые сессии/одноразовые ссылки не
дают доступа к новому кабинету. Если старого пароля нет, используется штатный
приватный setup-token. Существующий пароль сохраняется.

## Запуск первых двух аккаунтов

Когда импорт завершён, подключить действующие серверные конфигурации в новый
data root. Затем, ещё до запуска целевых исполнителей:

```bash
python -m qa_job_bot.maintenance on --data-dir /app/data/current
python -m qa_job_bot.pilot begin --owner-id OWNER_UUID
python -m qa_job_bot.cutover record --data-dir /app/data/current --services-stopped
python -m qa_job_bot.cutover rollback-status --data-dir /app/data/current --services-stopped
```

Команды используют приватный `DATABASE_URL`/`DATABASE_SCHEMA` из окружения и текущую
миграцию. `pilot begin` требует единственного включённого владельца-администратора;
повтор для той же пары настроек безопасен. Этот режим включают явно для переноса;
само обновление приложения не выключает существующие аккаунты.

`cutover record` требует pair, соответствующий импорт владельца в данный каталог,
текущую схему, отсутствие running/verifying/rendering и остановленные сервисы.
Сохраняет только хеши и количества. Начальная граница фиксируется до первого входа
и первого приглашения. Сигналы/управляющие поля `runtime_control` исключены; остальные
таблицы, включая сессии/попытки входа/расписания, и байты всех файлов сравниваются.
Оценка консервативная: служебная новая запись также требует сохранить и сверить
PostgreSQL перед решением об откате. `.maintenance` пуст и в файловый хеш не входит.

Запустить API и исполнителей в обслуживании без `--wait`: его API readiness пока 503.
Проверить конфигурацию/Origin и затем выключить обслуживание, дождаться healthy
сервисов. Для локального root переключатель:

```bash
python -m qa_job_bot.maintenance off --data-dir /app/data/current
```

В контейнерах команды выполняют через `maintenance` service из
`compose.runtime.yaml`, с тем же env file/project. Владелец входит под новым login
и прежним паролем; администратор создаёт ровно одного второго участника. До проверки
пары третий включённый/ожидающий аккаунт не появляется. Отключение ненужного pending
аккаунта освобождает место; отзыв или истечение ссылки само аккаунт не отключает.

## Проверка пары и расширение до 20 мест

Проверить на целевой установке:

| Поле отчёта | Фактическая проверка |
| --- | --- |
| `owner_history` | Старый пароль, вакансии, Applied/архив, source/template hashes и история сохранены |
| `search_professions` | Два разных направления поиска дают свои результаты и историю |
| `personal_states` | Applied/архив одного аккаунта не меняют состояние другого |
| `candidate_templates` | Два активных эталона/наборы фактов и исходные файлы независимы |
| `conversations` | Свои диалоги и сообщения, чужие IDs запрещены |
| `documents` | Проверенные DOCX/PDF доступны своему аккаунту, соответствуют фактам/хешам |
| `access_isolation` | Чужие tasks, sources, CV, artifact download/preview и SSE недоступны |

Оператор сохраняет JSON 0600 с `owner_id`, `tester_id`, точным `source_hash` импорта
и объектом `checks`, где семь полей выше имеют JSON `true`. Это результат реально
выполненных проверок. CLI проверяет структуру, import hash и текущие активированные
аккаунты; сами пользовательские проверки выполняются отдельно и отражаются в отчёте.
Содержимое CV, пароли и tokens в этот файл не включают.

```bash
python -m qa_job_bot.pilot expand --evidence /private/operator/pair-verification.json
python -m qa_job_bot.pilot status
```

Повтор того же отчёта идемпотентен. Другой владелец/source hash, неполные/ложные checks,
неактивированный/отключённый второй аккаунт не открывают cohort. Администратор видит
«Состояние закрытого пилота» и может обновить показания. После расширения допускаются
20 включённых/ожидающих аккаунтов вместе с владельцем; одновременные приглашения
и включения отключённых аккаунтов сериализуются. Публичной регистрации нет.

## Telegram

До включения нового polling убедиться, что старый процесс остановлен. Переносить
только явно проверенные chat IDs в соответствующий личный аккаунт; без такого
соответствия records остаются сохранёнными без активной привязки. Не выводить
соответствие автоматически из того, что ID был в общем старом allowlist.

Включить персональный service/profile после настройки private token и bindings
по `runtime-operations.md`. PostgreSQL lock не допускает второй новый процесс
в той же БД; старый SQLite polling и другой deployment этим lock не защищены.
Проверить личные команды, сохранённые deliveries, baseline и opt-out. В рамках
облачной подготовки внешний Telegram не запускался и сообщений не отправлялось.

## Возврат и сохранение нового прогресса

Снова включить обслуживание, остановить новые сервисы и сохранить их состояние.
`rollback-status --services-stopped` показывает наблюдаемое соответствие границе.
Он не останавливает процессы и не возвращает трафик автоматически. Даже положительный
результат действителен только при продолжающейся остановке всех писателей.

Если записи/файлы не изменились, при соблюдении остановки и режима обслуживания
`legacy_restart_allowed` истинно. Можно вернуть старый runtime с согласованной
копией и действующей конфигурацией, оставив новую установку остановленной.

При `preserve_postgres_and_files=true` простой возврат к старой SQLite запрещён.
Сначала сделать новый offline backup PostgreSQL вместе с files по эксплуатационной
инструкции, затем сверить изменения и подготовить перенос либо исправление новой
версии. CLI не удаляет новый прогресс и не перезаписывает исходную границу повторной
командой record. Доступность старой SQLite не означает, что в ней есть новые данные.
