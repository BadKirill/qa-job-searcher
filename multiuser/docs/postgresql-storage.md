# PostgreSQL и владение данными

Этап 1 [плана личных кабинетов](multi-user-development-plan.md). Целевая база —
PostgreSQL 17, SQLAlchemy 2.0.46, psycopg 3.3.2 и Alembic 1.18.1.
Фактические результаты проверок находятся в [журнале](verification.md).
Обновление этапа 3: общий веб-сервер определяет владельца по сессии;
[актуальный вход и bootstrap](accounts-and-access.md).

## Граница этого этапа

Реализован слой хранения с обязательным владельцем, модель пользователей,
персональные репозитории, общая публичная вакансия, персональные оценки/статусы
и внутренний репозиторий очереди. API и worker умеют использовать PostgreSQL;
основные API-тесты и все browser E2E выполняются на настоящей PostgreSQL.

Приглашения и получение владельца из пользовательской сессии реализованы
на этапе 3. Ниже сохранена граница первого слоя хранения: на этапе 1 экземпляр
приложения привязан серверной конфигурацией к одному существующему владельцу.
Этот режим нужен для разработки и проверки слоя хранения, а не для допуска
всех пользователей к одному общему входу.

SQLite и старые репозитории временно сохранены для работающей прежней версии,
регрессий старого формата и последующего импорта. Рабочий сервис и рабочие данные
этим этапом не переключаются. После проверенного импорта и полного перехода
поддержка SQLite как основного runtime-хранилища должна быть убрана.

## Подключение и миграции

`Database` принимает только PostgreSQL/psycopg URL. Пул проверяет соединения перед
использованием, ограничивает число соединений, задаёт connect timeout и UTC.
SQL-параметры скрыты в диагностике SQLAlchemy. Произвольные имена схем запрещены:
разрешены только строчные латинские буквы, цифры и подчёркивания, до 63 символов.

Миграция `0001_ownership` создаёт 30 таблиц приложения и служебную таблицу Alembic.
Она выполняется одной транзакцией с advisory lock, поэтому два процесса не
применяют начальную миграцию одновременно. Повторный upgrade не пересоздаёт таблицы.
Приложение проверяет ревизию и не заменяет миграции вызовом `create_all` при запуске.

Начальные DDL сохранены в неизменяемых `v0001_ownership.sql` и
`v0001_ownership_down.sql`, включённых в установочный wheel. Будущие изменения
моделей должны получать новые ревизии; менять SQL уже опубликованной миграции нельзя.
Интеграционный тест сравнивает получившуюся схему с моделями через Alembic autogenerate.
Downgrade используется в тестовой схеме; он не является способом безопасного
отката рабочей базы с новыми пользовательскими данными.

Переменные подключения:

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL URL, хранить как секрет конфигурации |
| `DATABASE_SCHEMA` | Схема приложения; по умолчанию `public` |
| `WEB_OWNER_ID` | Владелец промежуточного worker; общий веб-сервер его не использует |
| `QA_TEST_DATABASE_URL` | Отдельная PostgreSQL для тестов; не подменяется рабочим `DATABASE_URL` |

При заданном `DATABASE_URL` неверная миграция останавливает запуск. Worker
дополнительно требует существующий `WEB_OWNER_ID`; общий веб-сервер использует
аккаунт сессии. Незаметного перехода на SQLite/общего владельца при ошибке нет.
Без `DATABASE_URL` сохраняется прежний SQLite-путь до рабочего переключения.

Команда применения миграций после настройки `DATABASE_URL` и `DATABASE_SCHEMA`:

```bash
.venv/bin/python -m qa_job_bot.pg_database
```

Первого администратора создаёт защищённая команда `legacy_cli bootstrap`.
Для тестов слоя хранения остаётся `Database.create_user`. Отдельный `WEB_DATA_DIR`
не смешивает setup-token и файлы репетиции с прежней установкой.
[Импорт](legacy-import.md) добавлен ревизией `0002_legacy_import`; текущая ревизия
`0003_accounts` добавляет ограничения попыток и создателя одноразовых ссылок.
Порядок начальной настройки — в [accounts-and-access.md](accounts-and-access.md).

## Публичные и персональные данные

`PublicJobRepository` хранит только объявление и внешние идентичности. Фактическое
содержание строится из разрешённых полей `Job`; score, match_reasons,
location_status и resolved_fingerprint в публичный payload не попадают.
CHECK дополнительно запрещает персональные поля в общей записи.

`PostgresStore(database, user_id)` не имеет владельца по умолчанию. Он объединяет
персональные репозитории поиска, документов и заданий. Все их запросы ограничены
владельцем; публичного ID недостаточно для доступа к вакансии без своей записи
matching. Чужой ID возвращает 404, включая pagination snapshot.

| Данные | Хранение |
| --- | --- |
| Исходное объявление и source key | Общие `jobs`, `job_identities` |
| Score, причины совпадения и личная географическая оценка | `job_matches`, ключ пользователь–вакансия |
| Applied и архив | `user_jobs`, ключ пользователь–вакансия |
| Результат поиска и зафиксированные оценки | `search_runs`, `search_run_jobs` |
| Порядок страницы | Персональный `job_snapshots` |
| Эталон, диалог, сообщения, задание, файл | Обязательный user_id и персональные связи |
| Настройки и события | `user_settings`, `user_revisions` |
| Сессии и попытки входа | Привязаны к аккаунту; токены хешируются существующим Security |

Активация эталона и смена статуса используют короткую транзакцию с блокировкой
строки владельца. Это предотвращает потерю двух одновременных изменений одного
аккаунта; разные аккаунты не используют одну общую блокировку. Внутри такой
транзакции нельзя ждать сеть, модель или рендер файлов.

Составные внешние ключи запрещают связи с другим владельцем для шаблонов,
вакансий, диалогов, сообщений, заданий, файлов, usage и request ID. Дополнительные
CHECK связывают нормализованные template/job/conversation ID с закреплённым payload
задачи и требуют правильного owner_id в её контексте. Частичные уникальные индексы
разрешают только один активный эталон, профиль поиска и активную задачу одного scope
внутри аккаунта. Одинаковые request ID у двух людей независимы.

Изоляция обеспечивается персональными запросами и ограничениями связей. PostgreSQL
RLS в этом этапе не вводится; оператор с прямыми правами на базу остаётся отдельной
границей доверия. Нельзя выдавать приложению произвольный клиентский SQL или позволять
клиенту выбирать `WEB_OWNER_ID`.

## Очередь и жизненный цикл

`QueueRepository` — отдельный внутренний доступ для исполнителей. Он выбирает
queued-задания через `FOR UPDATE SKIP LOCKED`, исключает отключённые аккаунты,
записывает worker ID, lease и число попыток. Персональный store ограничивает захват
своим владельцем. Завершение проверяет worker ID, статус, владельца и lease;
поздний ответ после отмены не меняет результат.

Захват и завершение не удерживают транзакцию во время выполнения задания.
Проверены несколько одновременно работающих соединений/исполнителей, повторные
request ID, конкурентная активация шаблона, просроченный lease и отмена.
Heartbeat, персональные слоты, справедливое обслуживание, квоты и общий rate limit
OpenAI остаются задачами этапа 7. Возможность захвата несколькими исполнителями
не означает готовность общего gateway к параллельной работе.

Приложение закрывает свой пул PostgreSQL при завершении lifespan; worker —
в finally после своего цикла. В тестах жизненным циклом внедрённого репозитория
управляет fixture, чтобы несколько приложений могли разделять одну тестовую базу.

## Воспроизводимые проверки

Тестовая PostgreSQL запускается отдельно от приложения и публикует порт только
на localhost. Указанные credentials предназначены исключительно для локальных
синтетических тестов.

```bash
docker compose -p job-searcher-tests -f compose.test.yaml up -d --wait
export QA_TEST_DATABASE_URL='postgresql://job_searcher:local-test-only@127.0.0.1:55432/job_searcher_test'
.venv/bin/python -m qa_job_bot.quality
```

В управляемом облаке к последней команде добавить
`PLAYWRIGHT_BROWSERS_PATH=/workspace/qa-tools/ms-playwright`, если браузер установлен
в этом каталоге. Отсутствующая PostgreSQL или переменная тестовой базы делает
проверку неуспешной; пропуска с заменой PostgreSQL на SQLite нет.

Каждый PostgreSQL fixture создаёт случайную схему `qa_test_*`, применяет миграции
и удаляет только эту схему после завершения. Browser E2E использует две независимые
тестовые схемы для проектов Playwright. Внутри каждой есть два синтетических
владельца, поэтому проверка чужих ID выполняется в общей схеме, а не за счёт
разных баз. Один сценарий непосредственно проверяет отказ через браузерную сессию.

Главные API-тесты, PDF API и регрессии идемпотентности работают на PostgreSQL.
Старые SQLite unit/integration-тесты сохранены как проверки исходного формата
до импорта. Frontend проверяет персональные score/причины и обработку 404 снимка.
Coverage указывает путь `src/qa_job_bot`, чтобы учитывать фактическое исполнение
Alembic-файлов, загружаемых динамически, и не исключать миграции из измерения.

GitHub Actions получает PostgreSQL 17 как service с healthcheck. Локальное
прохождение не подменяет запуск GitHub CI; результаты внешнего CI фиксируются
отдельно после публикации изменений.

## Общий веб-сервер после этапа 3

PostgreSQL-вход веб-приложения теперь определяет владельца по сессии каждого
запроса; `WEB_OWNER_ID` остаётся только промежуточной конфигурацией worker.
Ревизия `0003_accounts` добавляет счётчики попыток и создателя одноразовых ссылок.
Текущие команды и контракты — в [accounts-and-access.md](accounts-and-access.md).
Описание привязанного экземпляра выше отражает этап 1 и старые регрессионные fixtures.

Ревизия `0004_search_settings` добавляет историю персональных подключений
`source_versions` и фиксирует текущие строки без изменения их параметров.
Контракт редактирования и проверки — [personal-search-settings.md](personal-search-settings.md).

Ревизия `0005_personal_runs` закрепляет личные карточки matching/запусков/снимков.
[Контракт запусков](personal-search-runs.md) описывает атомарную публикацию,
поздние результаты, свежесть, сохранение истории и границы downgrade.
