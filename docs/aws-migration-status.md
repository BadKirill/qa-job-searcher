## Резервирование и восстановление

Выполнен настоящий запуск `qa-job-searcher-backup.service`:
`daily-20261121T205227Z`, архив 17 356 228 байт. Архив, SHA-256 и digest загружены
в `backups/` S3. Этот архив затем заново скачан из S3, проверен по checksum,
восстановлен в отдельную БД с отдельными volumes и сравнен по всем строкам/файлам.
Результат совпал полностью. Временные БД, volumes, recovery env, скачанный
проверочный архив и две тестовые версии объектов `artifacts/offsite-restore-check/`
удалены. Оригинальные копии `backups/` сохранены.

Timer: ежедневно в 02:30 UTC с задержкой до 5 минут, `Persistent=true`.
Во время backup запись временно недоступна: включается maintenance, завершаются
активные задания, пять писателей останавливаются; после архивации запускаются
снова. В проверенном запуске сервис выполнялся примерно 43 секунды.
Ошибка upload не удаляет локальный архив. При сбое systemd повторяет backup
через 5 минут, не более трёх стартов за час. Это не замена внешнего оповещения.

Lifecycle из `infra/aws/backup-lifecycle.json` установлен только для
`backups/daily-`: текущие версии истекают через 14 дней, noncurrent версии
удаляются ещё через 14 дней после смены статуса. Таким образом, физическое хранение
в S3 может составить около 28 дней. Delete markers очищаются после удаления
версий, незавершённые multipart uploads прерываются через 7 дней.
Исходный архив миграции и `artifacts/*` этим правилом не затронуты.
После успешной отправки сервер удаляет только собственные локальные `daily-*`
старше 14 полных суток. Прежние копии Mac не удаляются.

Ежедневное резервирование допускает потерю изменений примерно за сутки при
отказе диска. Один EC2 и одна зона не обеспечивают высокой доступности.
При аварии нужно сохранить повреждённое состояние, создать чистое назначение,
восстановить согласованную копию и проверить её до переключения трафика.
Рабочая роль EC2 не читает `backups/*`: для восстановления оператор с нужными
правами передаёт выбранную копию в `artifacts/*` или выдаёт временную ссылку,
не расширяя постоянные права приложения. Открывать bucket для этого нельзя.

## Эксплуатация

В SSM-сессии сервера:

```bash
cd /srv/qa-job-searcher
dc() {
    sudo docker compose -p job-searcher-aws --env-file .runtime/runtime.env -f compose.runtime.yaml -f compose.aws.json "$@"
}
dc ps -a
sudo systemctl status qa-job-searcher.service qa-job-searcher-tunnel.service
sudo systemctl list-timers qa-job-searcher-backup.timer
sudo systemctl start qa-job-searcher-backup.service
sudo cat /var/lib/qa-job-searcher/last-backup
```

Не запускать backup одновременно с ручным restore или обновлением. Для обновления
сначала выполнить quality gate release в изолированной БД, сделать backup,
сохранить текущий image и запланировать maintenance. Использовать сохранённый
Compose override с закреплённым образом PostgreSQL. Не выполнять `down --volumes`
или global Docker prune на рабочей установке. Приватные env, backup и логи не
публиковать в GitHub.

Три CloudWatch alarm созданы, email/SNS actions пока не настроены. Отдельные
оповещения о неуспешном backup, заполнении диска и недоступности HTTPS не настроены.
Следующий полезный шаг — внешний мониторинг этих событий. Для аудита доступа S3
можно включить access logging, CloudTrail data events и CloudWatch request metrics;
платные расширения мониторинга не включались при выборе минимальной стоимости.
