# CI/CD GetCareer

23 ноября 2026. Целевое приложение находится в `multiuser/`, production URL —
https://getcareer.app. Сохранённая SQLite-версия в корне проверяется отдельно.

## Обязательные проверки

Единый workflow `CI` вызывает оба полных quality gate и Docker-репетицию
многопользовательского runtime. Gate блокируется при любой неуспешной обязательной
проверке. Backend и frontend каждой версии сохраняют независимые пороги 90%
исполняемых строк и 90% ветвлений по всему собственному исходному коду.
JUnit, Vitest JSON и Playwright JSON дополнительно проверяются: ноль failed,
errors, skipped, todo и flaky, ненулевое число проходящих тестов. Повторные
попытки Playwright выключены. Неисполненные сценарии не считаются успешными.

Ruff проверяет Python lint/формат; ESLint проверяет TypeScript/React. Radon
публикует сложность функций и maintainability index. Историческая сложность не
скрывается исключениями, но её отчёт не является числовым merge gate. Названия
и архитектурный смысл дополнительно проверяются при PR review; ни один из этих
инструментов не доказывает человекочитаемость автоматически.

CodeQL `security-and-quality` анализирует Python, JavaScript/TypeScript и Actions;
HIGH/CRITICAL security findings и error-level замечания качества блокируют gate.
Python-анализы legacy и multiuser разделены, чтобы одноимённые пакеты с разными
сигнатурами не смешивались; оба набора исходников и CI helpers проверяются. Bandit блокирует новые замечания средней
и высокой тяжести с высокой уверенностью. Единственное явно разобранное B310
относится к health URL из доверенного серверного окружения: код проверки не
получает пользовательского URL и не раскрывает ответ. Исключение привязано к
пути, rule ID и хешу точного кода, действует до 1 февраля 2027; изменения или
истечение срока снова блокируют gate. Это не общее отключение правила.

`pip-audit` проверяет три Python lock-набора, `npm audit` — три frontend/CI набора
и блокирует moderate и выше. Gitleaks проверяет Git-историю. Trivy проверяет IaC
и готовый ARM64 image, блокируя HIGH/CRITICAL. Неисправимые замечания не скрываются
флагом ignore-unfixed.
Для IaC два решения перечислены в `ci/trivy-reviewed.yaml` с точными путями и
сроком до 1 февраля 2027: исходящие TCP 80/443 к динамическим внешним адресам
и SSE-S3 вместо платного customer-managed KMS key. Входящие правила этим не
расширяются; остальной исходящий трафик запрещён. Уведомления CVE не исключаются.
Формат scoped/expiring decisions описан в [документации Trivy](https://trivy.dev/docs/latest/guide/configuration/filtering/). Actions закреплены по полным commit SHA; CI-зависимости
закреплены с хешами. Dependabot alerts и secret-scanning push protection включены.
Отчёты содержат только код и синтетические тестовые данные, срок хранения 7 дней.

## 99% стабильности

Пользователь подтвердил: 100% обязательных тестов в каждом прогоне, отдельно
целевая стабильность CI >=99%. Workflow `Current CI and reliability report` считает последние
100 завершённых push-прогонов `CI` в `master`, объединяя GitHub API с архивом
`ci/production_ci_history.json` по run ID. Свежая запись API имеет приоритет;
результаты сортируются по времени создания. Успех только с первой попытки;
rerun, failure и cancellation уменьшают показатель. Результат ниже 99% отмечается
warning и `target_met=false` в отчёте; цель не считается достигнутой.
Пустая или малая выборка не является доказательством будущей стабильности.
Отчёт запускается после production push CI и вручную, без ежедневного cron.
Старые сбои не создают повторные failed-job письма. Ошибка завершённого CI для
текущего master commit по-прежнему завершает отчёт ошибкой; устаревшие commits
и ещё выполняющийся актуальный CI не объявляются новым сбоем.
Reliability не блокирует исправляющий CD:
блокировка по прошлым сбоям могла бы запретить доставить сам фикс.

## Повторные запуски и обновления зависимостей

Полный CI запускается на pull request, push в master и вручную. Push в ветку
открытого PR не создаёт второй независимый набор тех же дорогих проверок.
Merge gate и проверка production после слияния остаются обязательными.

Dependabot объединяет npm minor/patch и Python minor/patch обновления по
экосистеме и каталогам; Vite, React plugin и Vitest обновляются одной группой,
включая major. Остальные major остаются отдельными PR для проверки совместимости.
Лимит version PR снижен до двух на конфигурацию. Security updates имеют отдельные
группы и не отключены лимитом version PR; ignore-правил для уязвимых версий нет.
React plugin 5.2.0 поддерживает Vite 7 и 8: отдельный PR Vite 8 больше не должен
падать на peer dependency conflict со старым plugin 5.0.4.

Загрузка зависимостей в CI и runtime из PyPI использует socket timeout 60 секунд,
пять сетевых повторов. Неподдерживаемый базовым pip resume-флаг не используется.
Ошибки установки по-прежнему останавливают сборку; тесты и их результаты
не перезапускаются для скрытия ошибок. Lock-файл и проверка хешей сохранены.

Vitest выполняет файлы максимум в двух workers. В GitHub выявлен тайм-аут
длинного component-сценария пагинации/applied/архива при параллельной нагрузке
jsdom; локально он проходил за 1,1 секунды. Ограничение параллельности снижает
конкуренцию за CPU runner. Тайм-аут теста 5 секунд, все assertions и запрет
повторов сохранены; каждый набор обязан пройти целиком.

При проверке инцидента 23 ноября production commit 20877fc имел шесть healthy
контейнеров, активные Caddy/app/backup timer и 24 успешные внешние HTTPS-проверки.
Красные Dependabot PR относились к прежней основе CI, конфликту Vite/plugin и
тайм-ауту PyPI. Исторический reliability 1/2 (50%) остаётся нарушением цели 99%,
даже при доступном приложении. Production push CI сохраняется для измерения
истории первых попыток и аудита релизов.

24 ноября по запросу владельца устаревшие runs закрытых PR, прежних веток,
одноразовых Dependabot jobs и повторяющегося исторического монитора очищаются
после сохранения метаданных. Остаются последний production push run текущего
master и последний CI актуального head каждого открытого PR. Перед удалением
production runs метаданные сохраняются в версионируемом JSON. Три исходных
production run, включая первоначальный неуспешный, остаются в расчёте: 2/3,
66,67%. Новая конфигурация отчёта вступает в силу после слияния общего PR.

## Доставка

Production запускается только из `master` и после `CI gate`. Ветки/PR не имеют
доступа к production environment. Сборка выполняется на GitHub-hosted ARM64,
на сервер передаётся готовый образ, Compose и Caddyfile. Тестовые/сборочные
задания не получают AWS-ключей, OpenAI-ключей, рабочих БД или исходных CV.

OIDC role `qa-job-searcher-github-deploy` доверяет только environment production
репозитория BadKirill/qa-job-searcher. Точный subject:
`repo:BadKirill@158462832/qa-job-searcher@1404647213:environment:production`.
Он сверён с GitHub OIDC customization API (`use_immutable_subject=true`), включает
неизменяемые ID владельца и репозитория; старый формат без ID не разрешён.
GitHub environment разрешает только master и запрещает admin bypass.
Роль может записывать только `artifacts/releases/*` в приватный S3 и запускать
только `qa-job-searcher-deploy` на `i-030fa1abecd9da0ac`; IAM, произвольный shell,
чтение backups и пользовательских credentials ей не предоставлены.
`GetCommandInvocation` имеет resource `*`, потому что операция не поддерживает
ограничение на ARN отдельной команды. Долгоживущих AWS или SSH-ключей в GitHub нет.

Установленный root helper проверяет SHA-256 manifest и каждого payload, source
revision label, ARM64 и конфигурацию Caddy, затем берёт общий lock с backup.
Manifest v2 связывает SHA-256 всего архива с переносимым fingerprint: все
упорядоченные rootfs layer digests, архитектура/OS и параметры выполнения образа
(User, Env, Cmd, Entrypoint, WorkingDir, ports, volumes, labels, signal, shell,
healthcheck, OnBuild). Пустые Docker/OCI defaults нормализуются; opaque Docker ID
сохраняется для аудита, но может измениться при import между движками.
Изменение слоя, команды, окружения или пользователя блокирует доставку.
Перед изменением выполняется согласованная offsite-копия. Приложение закрывает
запись, задания завершаются, писатели останавливаются; заменяются конфигурация и
image, проходят миграции и реальные healthchecks. Maintenance выключается перед
проверкой readiness: в режиме обслуживания readiness намеренно возвращает 503.
Проверка всех служб и внешняя матрица 200/401/404 обязательны для успешного CD.

При ошибке прежний image/config возвращаются только если revision БД не изменилась.
При смене схемы остаются maintenance и остановленные писатели: автоматическое
восстановление старой БД могло бы уничтожить новые данные. Нужна проверка оператором.
Если ожидание SSM завершилось timeout, сначала проверяют уже отправленную команду;
новый платный/изменяющий запуск автоматически не отправляется.

Шаг доставки записывает в лог этапы загрузки release и отправки SSM, а в
GitHub Actions Summary выводит SHA, идентификатор команды, состояние, детали SSM,
код выхода и длительность. Опрос пишет переходы состояния и периодические
сообщения; ошибки чтения, включая `InvocationDoesNotExist`, показаны отдельно от
`Pending`. Команда в состоянии `Cancelling` остаётся под наблюдением до
окончательного статуса или таймаута. Завершившаяся команда оставляет вывод
в логе задания. [Состояния SSM Run Command](https://docs.aws.amazon.com/systems-manager/latest/userguide/monitor-commands.html)
Ошибка `shared_backup_deploy_lock_busy` означает остановку до подготовки релиза.
GitHub Actions не определяет, кто держит общий lock. При разборе сопоставляют
время команды SSM с журналом backup/deploy на сервере.
Ошибка `runtime_health_check_failed` выделяет отказ проверки здоровья после
запуска. Сводка отмечает, если в выводе этой же команды Compose также исчерпал
ожидание здоровых служб. Доступность HTTP сама по себе не подтверждает успешный
откат всех контейнеров.

Исходники инфраструктуры: `infra/aws/cicd.json`, `domain.json`, Caddyfile и
Compose override. Старый ручной workflow Deploy VPS удалён: он относился к другой
версии и мог обходить новые gates. Удаление workflow не удаляет сохранённые данные.

Actionlint, Ruff и ESLint прошли. После обновлений npm audit и pip-audit не находят

отклоняет results без метаданных. Ранний зелёный CodeQL gate не учитывал extensions;
это исправлено регрессией, результаты требуют повторной проверки. Удаление документа
использует канонический ID из авторизованной записи и запрещает компоненты пути;
Caddyfile устанавливается атомарно с правами root:caddy 0640.
CodeQL считает групповое чтение потенциальным раскрытием данных. Для этого одного
finding в `ci/codeql-reviewed.json` зафиксирован пересмотр до 1 февраля 2027:
Caddy работает непривилегированно и должен читать публичные правила маршрутизации.
В конфигурации нет секретов; caddy не может её писать, остальные пользователи не
могут читать. Разрешение привязано к rule ID, пути, строке и SHA-256 целиком
`ci/deploy.py` и Caddyfile. Любое изменение кода/конфига, новая локация или истечение
срока снова блокируют gate; регрессии проверяют каждый отказ. Path injection и
проверки URL исправлены в коде и тестах, исключения для них отсутствуют.

Production runtime переведён с Debian на Python 3.12 / Alpine 3.24 после того,
как image scan выявил неисправленные Debian CVE. Локальный ARM64-кандидат прошёл
Trivy с нулём HIGH/CRITICAL без ignore-unfixed и исключений CVE. PostgreSQL 17
client и DejaVu сохранены; стандартный путь шрифтов совместим с прежним рендером.
Внутри готового образа выполняются 119 проверок PDF/DOCX/layout/template; это
дополнительно проверяет musl/PDFium и шрифты. Реальная Docker-репетиция подтвердила
6 healthy служб, backup, restore login/file и stop/start. Она использует только
отдельные синтетические volumes, не рабочую БД.

Финальный CI, ARM64 image scan и первая автоматическая доставка требуют успешных
завершённых runs. Актуальные результаты публикуются в [Actions](https://github.com/BadKirill/qa-job-searcher/actions/workflows/ci.yml)
и [production deployments](https://github.com/BadKirill/qa-job-searcher/deployments).
Наличие YAML само по себе не означает рабочий CI/CD. Контролируемые внешние ответы
в regression gate не доказывают доступность живого OpenAI API/MCP; production
credentials и личные документы не передаются в GitHub Actions.

## Первый запуск OIDC

В первой попытке master run [45100483824](https://github.com/BadKirill/qa-job-searcher/actions/runs/45100483824)
все quality/security/image gates прошли, CD остановился до передачи артефакта:
AWS trust policy использовала прежний subject без immutable ID.
GitHub для этого репозитория выдаёт новый формат, подтверждённый API и
[OIDC reference](https://docs.github.com/en/actions/reference/security/oidc).
Trust исправлена на точный immutable subject без расширения разрешений.
Сбой первой попытки остаётся в истории reliability, даже если повторная доставка
успешна; текущая малая выборка не удовлетворяет цели 99%. Это не пропуск тестов.

Первый доставленный архив также выявил несовместимость opaque image ID: Docker
на GitHub и EC2 сохранил одинаковые слои и runtime-конфигурацию с разными ID.
Guard остановил prepare до backup/переключения. Для v2 переносимый fingerprint
проверен на реальном остановленном кандидате EC2 и исходном archive config.
Контроль SHA-256 payload и label commit сохранён. Прежние manifests v1 отвергаются.

Исправленная CloudFormation-конфигурация прошла cfn-lint 1.61.0 и Trivy.
cfn-guard 3.3.0 с IAM rules registry commit
`7f7340c26ae5d5e8874651dbffeb12e0e9f505b6`: 6 applicable PASS, 2 not applicable,
0 violations. Это отдельная проверка правил IAM, не аттестация всех сервисов AWS.
