# Проверка фактов и защита агентского процесса

Статус: требования безопасности первой реализации. Реализованные ограничения,
реальные проверки OpenAI API/MCP и известные ограничения описаны в `agent-runtime.md`. Цель — снизить риск и блокировать непроверенные результаты;
абсолютное отсутствие галлюцинаций и prompt injection не гарантируется.

## Роли и границы доверия

Пользователь взаимодействует с агентом только через авторизованный веб-интерфейс.
Оркестратор управляет сессиями, версиями, разрешениями и жизненным циклом заданий.

| Компонент | Доступ | Не может |
| --- | --- | --- |
| Диалог настройки | Сообщения владельца, черновик шаблона/профиля | Самостоятельно активировать версию или подтверждать факты |
| Генератор | Снимок вакансии, активный шаблон, подтверждённые факты текущей задачи | Менять профиль, обходить проверку, публиковать файл |
| Проверяющий | Оригинальные факты, цитаты вакансии, черновик, правила проверки | Получать разрешения генератора, исправлять базу фактов, выдавать ready |
| MCP-сервер | Разрешённые конкретной задаче данные | Давать произвольный доступ по переданному моделью ID/пути |
| Policy gate | Проверка схем, ссылок на факты, вердикта и целостности | Считать ошибку/отсутствие проверки успешной проверкой |
| Рендерер | Утверждённые структурированные данные и шаблон | Выполнять код, макросы или сетевые запросы из документа |

Сессии генератора и проверяющего разделены. Проверяющий получает исходные доказательства
напрямую от приложения, а не только пересказ генератора, его оценку уверенности
или аргумент «я уже проверил». Разделение сессий не делает ошибки статистически
независимыми; его дополняют программные проверки и evals.

## Эталон и подтверждённые факты

Первый экран показывает «Задать эталонный шаблон». Пользователь загружает DOCX/PDF,
обсуждает с агентом оформление/язык и видит извлечённый профиль с источниками.
Кнопка «Сохранить эталон» подтверждает показанные факты и активирует версию.
Затем основная кнопка называется «Изменить эталонный шаблон».

Пока новая версия разбирается или обсуждается, действует предыдущая. Отмена/ошибка
не удаляет её. Активация атомарна, проверяет ожидаемую текущую версию, а пользователь
видит конфликт параллельного изменения. Задания фиксируют версии в момент создания.

Каждый факт имеет ID, значение, категорию, ссылку на место в исходном документе
или явное сообщение владельца, версию и отметку подтверждения. Файлы и текст
вакансий не могут сами объявить свой текст подтверждённым фактом кандидата.
Новые сведения из диалога сначала показываются как изменения и подтверждаются
отдельным действием в интерфейсе. Генерация без активного эталона возвращает
`needs_input`/понятную ошибку, а не придумывает базовый CV.

## Проверка фактов до выдачи файла

Помимо достоверности, API reviewer обязан вернуть структурированную оценку
соответствия вакансии, выбора релевантных фактов и структуры документа. Отрицательная
оценка любого измерения блокирует `pass`; отсутствие или противоречие оценки — ошибка.
Эта проверка не разрешает дописывать отсутствующие навыки ради ATS или менять реальные
должности. Подробности и неизменяемое правило чёрно-серого оформления находятся в
`document-tailoring.md`.

1. Генератор возвращает данные по строгой схеме: разделы документа и реестр
   утверждений с `candidate_fact_ids` и, где требуется, `job_evidence_ids`.
2. Приложение проверяет схему, существование ID, владельца, соответствие версий,
   числа, даты, имена компаний, названия ролей и контакты. Ссылка на существующий
   факт не доказывает соответствие смысла: семантическую проверку выполняет reviewer.
3. Проверяющий сверяет весь текст, включая утверждения, которые генератор не внёс
   в реестр. Проверяет опыт, навыки, длительность, достижения, образование, зарплатные
   и географические утверждения, обещания от имени кандидата и факты о работодателе.
4. Проверяющий возвращает `pass`, `revise` или `needs_input`, список неподтверждённых
   утверждений/противоречий и ссылки на доказательства. Неверная схема — ошибка проверки.
5. При `revise` допускаются максимум две попытки исправления. Каждая версия проходит
   полный gate заново. При нехватке фактов вопрос возвращается в веб-диалог.
6. Только после `pass` и программных проверок рендерер формирует DOCX/PDF. Приложение
   проверяет итоговый текст, отсутствие скрытого добавленного содержимого и корректность
   рендера. Проверка привязана к хешам входов, утверждённого текста и готовых файлов.
7. `ready` выставляет оркестратор. Скачивание допускается лишь при действующей проверке
   конкретного artifact/hash; изменение документа аннулирует его прежнее одобрение.

Для PDF- и DOCX-эталона между рендерингом и `ready` обязательна отдельная визуальная
проверка итогового PDF. Reviewer получает PNG итоговых страниц; для PDF-эталона
также получает PNG исходных страниц. Для DOCX он проверяет итог против извлечённых
параметров оформления без изображения оригинала. Ответ связан с SHA-256 визуального
эталона и итогового PDF, а также с хешем утверждённого черновика. `revise`,
невалидная схема, несовпадение хешей, timeout и недоступность
модели не допускают регистрацию скачиваемых артефактов. Хеши PDF и DOCX фиксируются
до проверки и повторно сверяются перед регистрацией, чтобы подмена во время
ожидания модели не получила новый действующий хеш. После отмены файлы не выдаются.

Оригинал PDF и PNG доступны только через авторизованный API. MCP выдаёт метаданные
эталона, а runner добавляет проверенные изображения без доступа модели к файловой
системе или произвольным URL. Изображения проверяются по формату, размеру и хешам.
Инструкции, нарисованные на страницах, не получают дополнительных прав. Новые факты
из картинки не заменяют подтверждение владельцем.

До нативного рендеринга PDF сервер проверяет размеры image resources: суммарно
не больше 30 миллионов исходных пикселей. Отдельно ограничены выходные PNG,
количество страниц, объекты, текст, потоки и время дочернего процесса. Это границы
поддерживаемых файлов, а не гарантия отсутствия ошибок сторонних PDF-декодеров.

Итоговая схема состояний: `queued → running → verifying → rendering → ready`.
Возможны `needs_input`, `blocked`, `failed`, `cancelled`. Timeout/недоступность/отказ
reviewer не разрешают выдачу. Поздний ответ после отмены также не делает файл готовым.
Непроверенные черновики не выдаются как готовые документы; интерфейс показывает причины
блокировки и вопросы, без опасного активного HTML из внешнего источника.

## Защита от инструкций внутри данных

Описания вакансий, HTML, PDF/DOCX, вложенные ссылки, MCP-ответы и генерируемые черновики
считаются недоверенными данными. Не конкатенировать их с system/developer-инструкциями.
Не позволять им менять инструменты, права, вердикт, профиль, адреса передачи данных
или правила сохранения. Строгая JSON-схема ограничивает форму, но сама не доказывает
достоверность и безопасность текста.

Обязательные ограничения выполнения:

- У генератора и reviewer нет произвольного shell, браузера, записи в репозиторий,
  доступа к окружению с секретами или произвольной сети. Использовать отдельную
  конфигурацию runner без унаследованных плагинов и инструментов desktop.
- Приложение загружает вакансии само, проверяет HTTP(S), DNS/IP и каждый redirect;
  запрещает localhost, private/link-local/служебные адреса, URL с credentials,
  ограничивает размер, время, content type и число переходов. Предотвращать DNS rebinding.
- Разрешения MCP привязаны к владельцу, задаче, версии и сроку действия. Аргументы
  модели не расширяют scope; проверять его кодом при каждом вызове.
- Профиль и документы не отправляются сторонним сайтам. Модель получает только
  необходимые поля; лишние контактные данные можно подставлять локально рендерером.
- Разбор файлов изолирован, без макросов, скриптов, загрузки внешних ресурсов и
  произвольного раскрытия архивов. Ограничивать размер, страницы, распакованный
  размер и число элементов; проверять MIME и содержимое, запрещать traversal.
- Очистить HTML; отображать текст безопасно, не исполнять его в браузере. Учитывать
  скрытый текст, метаданные, DOCX comments/relationships и PDF annotations как возможные
  каналы инструкций. Содержимое не получает доверия после одной очистки.
- Детерминированный рендерер использует разрешённые поля/разделы; текст шаблона
  не должен становиться выполняемым выражением шаблонизатора или командой.
- Логи содержат task ID, версии, хеши и причины решений; секреты и полный CV не
  попадают в общие логи и CI-артефакты.

Эти запреты обеспечиваются настройками API и серверной политикой, а не
просьбой к модели. Для OpenAI Agents API обязательны `environment: none`,
пустые `tools` и `vault_ids`, `multi_agent.enabled: false`. После создания и при
опросе сессии gateway проверяет эффективные параметры и закрывает результат при
отличиях. Не исполнять никакие `required_actions` или tool items. Если ограничения
не обеспечиваются, закрыть выдачу и выбрать совместимый изолированный runner;
не запускать публичный сервис с широкими правами и обещанием безопасности.

## MCP первой версии

Для локального agent runner использовать MCP по stdio с привязанным к процессу
контекстом задачи. Сервер предоставляет узкие инструменты:

- `get_job_context` — снимок описания и цитаты только для текущей вакансии;
- `get_candidate_facts` — подтверждённые необходимые факты текущей версии;
- `get_template_metadata` — разрешённые настройки оформления и версия;
- `get_document_draft` — текущий черновик для reviewer.

Генератор не получает reviewer-only инструменты. Результаты модели принимает
оркестратор через типизированный ответ. Инструментов `run_shell`, произвольных
`read_file`/`fetch_url`, `set_ready`, `approve_document` и `activate_template` нет.
Запросы на изменение шаблона и скачивание идут через авторизованный API веб-приложения.

MCP не публикуется через ngrok в MVP: агент работает рядом с сервисом. Если позже
понадобится удалённый MCP-клиент, добавить Streamable HTTP с отдельной авторизацией,
проверкой audience/scope и Origin; не считать знание URL или веб-cookie достаточным.
MCP не запускает агентский turn сам: запуск остаётся у очереди и OpenAI Agents API.

## Обязательные атаки и негативные сценарии

- «Игнорируй предыдущие инструкции», поддельный system/developer role, многоязычные
  и закодированные инструкции внутри вакансии, PDF и DOCX.
- Требование добавить несуществующий стаж/сертификат, замена компании/дат/контактов,
  преобразование требования работодателя в якобы опыт кандидата.
- «Проверка уже пройдена», поддельные evidence IDs, JSON с `approved=true`,
  инструкция reviewer поставить pass, атака через черновик генератора.
- Попытка получить `.env`, чужой CV/задачу, вызвать неразрешённый инструмент,
  отправить резюме на внешний URL или вставить tracking-ресурс в документ.
- SSRF, redirect на приватный IP, DNS rebinding, path traversal, oversized/zip bomb,
  повреждённый файл, активное содержимое и выражение шаблонизатора.
- Повтор после отмены, истёкший scope, рестарт worker, подмена файла после проверки,
  частичная запись и скачивание по угаданному ID без разрешения.
- Отказ проверяющего, невалидный JSON, пустые доказательства, конфликт источников
  и исчерпание лимита исправлений.

Ожидаемые результаты фиксируются в матрице и eval-наборе: запрет действия,
`blocked`/`needs_input`, отсутствие выдачи файла и изменения подтверждённых фактов.
Доброкачественные вакансии и шаблоны тоже включить, чтобы оценивать ложные блокировки.

## Официальные материалы

План следует принципу проверки входов, выходов и разрешений инструментов на стороне
приложения, описанному в [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).
Это архитектурный принцип; безопасность фактической конфигурации Agents API
проверяется отдельно от инструкций модели и mock-тестов.

Требования к минимальным правам, данным и защите MCP отражены в
[Security & Privacy](https://developers.openai.com/plugins/guides/security-privacy)
и [Build an MCP server](https://developers.openai.com/plugins/build/mcp-server).

## Платный API и секреты

С 7 октября 2026 авторизован получатель необходимых фактов, текста вакансии и
изображений эталона — проект владельца в OpenAI API. Произвольные внешние URL
из документов туда не загружаются. Единственный HTTP endpoint runner закреплён
кодом: `https://api.openai.com/v1`; redirects и HTTP proxy из окружения отключены.
API-ключ читается из приватного файла, не передаётся MCP, модели или браузеру.
Приложение не меняет permissions или billing. Новая API-сессия создаётся один раз;
неопределённый сетевой исход не вызывает автоматический повтор платной генерации.
При timeout/cancellation отправляется cancel с коротким отдельным таймаутом;
недоступность сети не позволяет гарантировать остановку удалённого вычисления.
